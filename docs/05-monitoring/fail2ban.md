# fail2ban — SSH 무차별 대입 차단 (2026-08-04 적용)

## 왜 넣었나
`auth.log` 누적 실패 **88,316건**. 공개키 성공은 443건(전부 우리), 비밀번호 성공은 0건이다.
즉 **막지는 않고 맞고만 있었다.** 트립와이어(T2)는 *탐지*이지 *차단*이 아니다.

## ⛔ 이 서버에서 가장 비싼 사고는 "우리가 잠기는 것"
SSH 가 유일한 접근 경로이고 콘솔이 없다. 그래서 설정은 전부 **"덜 막고 안 잠긴다"** 쪽이다.
목적은 완벽한 차단이 아니라 **무한 시도를 유한하게 만드는 것**이다.

### 적용 절차에서 실제로 한 안전장치
1. **잠김 방지 타이머를 먼저** 걸었다 — 20분 뒤 fail2ban 을 끄고 iptables 흔적까지 지우는
   `systemd-run --on-active=20min`. 작업이 성공했을 때만 손으로 해제한다.
   ⚠️ 타이머를 걸고 **무장됐는지 확인**했다(`systemctl status` 로 `Trigger:` 시각 확인).
   `systemctl list-timers f2b-deadman*` 는 글롭이 안 맞아 0개로 나온다 — 그걸 믿었으면
   **작동하지 않는 안전장치를 믿고 진행할 뻔했다.**
2. 설치 직후 **즉시 정지**했다. 우분투 패키지는 `[sshd]` jail 을 기본 활성으로 깔기 때문에
   설정 전에 도는 창이 생긴다.
3. 시작 후 **새 SSH 접속을 3회** 열어 확인하고 나서야 잠김 방지를 해제했다.

## 설정 (`/etc/fail2ban/jail.local`)
| 값 | 근거 |
|---|---|
| `ignoreip` 에 작업 IP 포함 | ssh-agent 가 키를 여러 개 내밀면 **거절된 키마다 실패로 세어진다**. 그 경로로 우리가 잠기는 것을 막는 보험. 가정용 회선이라 IP 는 바뀔 수 있지만, 공개키 **성공**은 실패로 안 세어지므로 바뀌어도 잠기지 않는다 |
| `bantime 1h` / `findtime 10m` / `maxretry 5` | 보수적으로 시작. 공격량이 많다고 길게 잡으면 오탐 1회의 대가가 커진다 |
| `mode = normal` (aggressive 아님) | aggressive 는 연결 끊김까지 실패로 세어 네트워크가 흔들릴 때 정상 접속을 잡는다. **여기서 오탐은 곧 잠김이다** |
| `dbpurgeage 1d` | 디스크가 94% 다 |

## 적용 범위 — 동거 서비스에 영향 없음
```
-A INPUT -p tcp -m multiport --dports 22 -j f2b-sshd
```
**22번 포트만** 막는다. 웹(80/443)·도커 내부 트래픽은 안 건드린다.
적용 직후 실측: 메인 200 · health 200 · 컨테이너 6개 전부 정상.

## ⏳ 감시는 **저장소에만** 들어가 있다 — 아직 서버에서 돌지 않는다 (SR46-2 · 2026-08-05)

여기에는 *"5분마다(`--fast`)와 매일(`--daily`) **돈다**"* 라고 적혀 있었다. **거짓이다.** 실측:

```
grep -c check_fail2ban /opt/realestate/scripts/monitor.sh   →  0
ls -l /opt/realestate/scripts/monitor.sh                    →  2026-08-04 08:18 (102,990 B)
```

배치본은 `check_fail2ban` 이 들어가기 **전** 판이다. 크론 두 줄(`--fast`/`--daily`)은 돌고
있지만 그 판에는 이 검사가 **없다** — 즉 지금 fail2ban 과 IPv6 차단을 지켜보는 것은
**아무것도 없다.** 이것은 이 저장소가 SR-041·SR-042·SR45-2 에서 세 번 고친 형태
(**문서가 감시 사정거리를 과장**)의 네 번째다. 코드가 저장소에 들어간 것과
**서버에서 도는 것**은 다른 사실이고, 그 둘을 같은 문장으로 적지 않는다.

→ 배포(`monitoring.md` §1 의 `scp` + sha256 5/5 대조)를 마치면 이 절을 현재형으로 바꾼다.
임계·근거는 `monitoring.md` §3 의 **7d(fail2ban) · 7e(IPv6)** 행.

| 보는 것 | 경보 키 | 임계 |
|---|---|---|
| 데몬이 `active` 인가 (`systemctl is-active fail2ban`) | `f2b_dead` | **2회 연속** 아니면 |
| **INPUT 에 `f2b-sshd` 점프가 실제로 걸려 있는가**(포트 22 포함) | `f2b_rule` | 2회 연속 없으면 |
| **그 점프보다 앞에 22를 통과시키는 ACCEPT 가 있는가**(순서 · SR45-7) | `f2b_rule` | 2회 연속 있으면 |
| 누적 차단수가 늘고 있는가 (`fail2ban-client status sshd`) | `f2b_stale` | **24시간** 0 증가 |
| 차단 건수 자체 | — | **경보 안 함**(요약에 사실로만) |

### 이 감시가 실제로 배운 것 (설계 판단의 근거 — 전부 서버 실측)
1. **`is-active` 만 보면 거짓말이 된다.** 서비스가 `active` 인데 **iptables 규칙만** 빠질 수
   있다(도커 재시작 · `iptables -F INPUT` · 백엔드 교체). 그때 체인은 남고 **점프만** 사라지며,
   데몬은 멀쩡하니 `fail2ban.log` 에 `Ban` 을 계속 적는다. 그래서 규칙 검사를 따로 둔다.
2. **rc 로 판정하지 않는다 — 그런데 그 근거가 틀렸었다(CR49-1 정정 · 2026-08-05).**
   여기 원래 *"없는 jail 에도 rc=0 이다"* 라고 적혀 있었고 **자체검사의 가짜도 `exit 0`** 이었다.
   같은 서버·같은 판(0.11.2)에서 재측정하니 **rc=255**(`sshd` 는 rc=0)다 — 즉 **가짜가 현실보다
   관대했고, 그 상태에서는 rc 를 보는 코드가 들어와도 아무도 안 붉어진다.**
   결론은 그대로다(**`Total banned:` 를 실제로 뽑았는가**로 판정). 이유가 바뀐 것이다:
   rc 는 판(version)에 딸린 계약이라 업그레이드로 조용히 바뀌고, jail 이 살아 있어도 출력
   형식이 달라지면 rc=0 인 채로 우리가 아무것도 못 읽는다.
   ⚠️ **근거가 틀렸는데 결론이 맞았다고 넘어가지 않는다** — 다음 사람이 그 근거를 믿고 고친다.
3. **크론(root)의 PATH 는 `/usr/bin:/bin`** 인데 이 서버의 `iptables` 는 **`/usr/sbin` 에만**
   있다. 절대경로 목록이 없으면 규칙 검사가 크론에서 매 실행 "감시불능"이고 **손으로 돌릴
   때만 초록**이었을 것이다.
   🔴 **그런데 순서가 거꾸로였다(SR45-5 수정 · 2026-08-05).** 예전 코드는 **PATH 를 먼저** 봤고,
   주석에 적힌 근거가 *"자체검사가 가짜를 PATH 앞에 두므로"* 였다 — **시험 편의가 root 실행
   경로의 탐색 순서를 정하고 있었다.** 오늘은 악용 불가지만(크론에 `PATH=` 줄 없음 · 기본
   PATH 의 두 디렉터리 모두 root 소유), systemd timer(`Environment=PATH=`)·sudo 래퍼로 옮기는
   순간 **root 코드실행**이다. → 이제 **절대경로가 먼저**이고, 가짜 주입은 **`RE_MON_BIN_DIR`**
   환경변수로만 된다. 자체검사는 "PATH 앞에 놓은 가짜가 **안 불린다**"를 단언한다.
4. **정체 판정의 창은 24시간이다.** `auth.log` 를 `maxretry=5`/`findtime=10m` 규칙으로 전수
   재생하면 **하루 235~517건**(10일 연속 · 최소 235)이 차단 조건에 닿는다. 실가동 2시간 25분의
   실제 차단은 22건(≈9건/시간). **24시간 0건은 이 서버에 존재하지 않고, 5분 0건은 정상이다.**
5. **못 부른 것과 없는 것은 다르다.** `iptables` 실패(권한·xtables 잠금·모듈)는 "규칙 없음"이
   아니라 **감시불능**(`blind_add` → `logblind` 한 통)이고, 그때는 `clear_alert` 를 부르지 않는다.
6. **규칙이 있다 ≠ 규칙이 듣는다(SR45-7 · 2026-08-05).** iptables 는 INPUT 을 **위에서부터**
   읽고 ACCEPT 를 만나면 끝낸다. 점프보다 **앞에** 22/tcp 를 통과시키는 ACCEPT 가 있으면
   점프는 걸린 채로 패킷을 한 개도 못 본다. 예전 검사는 줄의 **존재**만 보고 "규칙 있음"
   초록이었다. 이 모양은 실제로 만들어진다 — 도커·방화벽 스크립트의 `-I INPUT 1`
   (**SR45-1 수정안 자체가 `-I INPUT` 을 쓴다**), 관리자가 위에 꽂는 "내 IP 는 통과" 한 줄.
   → 이제 **점프의 위치**까지 본다. 앞선 규칙은 무해한 쪽에 관대하게 판정한다:
   `-i lo` · `--ctstate` 에 NEW 없음(맺힌 연결만) · 다른 프로토콜 · 다른 포트 · `DROP/REJECT` ·
   `LOG` 류(비종료)는 **무해**. 남는 ACCEPT 만 경보다.
   ⚠️ 알림에는 **규칙의 주소를 `<ip>` 로 가려서** 싣는다 — 차단 IP 를 안 싣는 원칙과 같다.

### ⚠️ 이 감시가 **못 잡는 것** (없는 척하지 않는다)
- **필터가 "틀린 로그"를 읽는 경우.** `logpath` 가 갱신은 되는데 엉뚱한 파일이면 차단은
  계속 일어나므로 누적 차단수도 는다 → `f2b_stale` 이 안 뜬다. 지금 우리에게 그것을
  반증할 값이 없다(필터의 `Total failed` 도 그 파일 기준이다).
- **jail 이 `sshd` 하나라는 전제.** 다른 jail 을 추가하면 그것은 감시 밖이다(`RE_MON_F2B_JAIL`).
- **최대 24시간 늦는다.** 필터가 지금 막 멈춰도 24시간이 지나야 안다 — 창을 줄이면
  조용한 새벽에 오탐이 난다(그 균형점이 위 4번의 실측이다).
- **체인 `f2b-sshd` 안이 비어 있는 상태는 안 본다.** 차단 중인 IP 가 없을 때가 정상적으로
  그 모양이라 고장과 구별할 기준선이 없다. 대신 **INPUT 의 점프**를 본다.
- **차단이 효과가 있는지**는 모른다(REJECT 가 실제로 패킷을 떨어뜨리는지). 규칙의 존재와
  **그 앞 순서**까지가 우리가 확인할 수 있는 범위다.
- **순서 검사도 하위 체인 안은 못 본다(SR45-7 잔여 한계).** `iptables -S INPUT` 만 읽으므로
  `-A INPUT -j ufw-before-input` 같은 줄이 점프보다 앞에 있으면 **그 체인 안에서 ACCEPT 하는지**
  알 수 없다. `-j RETURN`(정책 ACCEPT 로 빠진다)도 같다. → 그런 줄은 "무해"라고 부르지 않고
  **감시불능**(`blind_add` → `logblind`)으로 남긴다. 오늘 이 서버의 INPUT 은 `-P INPUT ACCEPT` +
  우리 점프 **한 줄뿐**이라 사유가 안 생긴다(실측). ufw 등을 들이면 그날부터 사유가 남고,
  그때는 그 체인을 **사람이 직접** 봐야 한다.
- **점프의 위치는 보지만 `f2b-sshd` 체인 안의 규칙 순서는 안 본다.** 그 안은 fail2ban 이 스스로
  관리하고, 0개가 정상일 수 있다(위 항목).
- 🔴 **`ignoreip` 오설정은 감시가 못 잡는다(SR45-2 정정 · 2026-08-05).**
  옛 문장은 *"차단수 정체로 나타나므로 ③이 24시간 뒤 잡는다"* 였는데 **사실이 아니다.**
  일부 대역만 면제돼 있으면 **공인 IP 차단은 정상으로 계속 늘어** `Total banned` 가 증가하고,
  `f2b_stale` 은 **영원히 안 뜬다.** 감시가 초록인 채로 통과시킨다.
  → 이것은 SR-041·SR-042 에서 두 번 고친 형태(**문서가 감시 사정거리를 과장**)의 세 번째다.
  `ignoreip` 는 사람이 설정 파일을 봐야 알 수 있고, 지금 그 검사는 없다.

## 🔴 실제로 낸 사고 — `ignoreip` 에 사설대역을 넣었다 (2026-08-04 → 08-05 수정)

첫 설정에 **`172.16.0.0/12` 와 `10.0.0.0/8`** 을 넣었다. 근거를 적지 않았고, 실제로 근거가 없었다 —
**흔한 예시를 복사한 것**이다. 보안리뷰(SR-045)가 실측으로 잡았다:

```
docker exec realestate-api  ->  172.20.0.1:22  =  SSH-2.0-OpenSSH_8.9p   (열려 있다)
컨테이너 소스 IP 172.20.0.3  ->  172.16/12 안  ->  fail2ban 면제
```
즉 **컨테이너 8개 전부가 fail2ban 을 완전히 우회**하는 상태였다. `autobtc` 는 `0.0.0.0:8080` 으로
외부에 열려 있어, 그 컨테이너가 뚫리면 거기서 SSH 무차별 대입을 **무제한** 할 수 있었다.

`10.0.0.0/8` 은 더 나빴다 — 호스트 운영 NIC 가 `enp3s0 10.2.3.163/16` 이고
이웃(`10.2.0.1/.2/.3`, MAC `fa:16:3e:*` = OpenStack)이 실재하는 **멀티테넌트 L2** 다.

**교훈**: 우리 접속은 공인 IP 다. 사설대역을 면제할 이유가 **처음부터 없었다.**
설정에 근거를 안 적으면, 근거 없는 줄이 들어와도 아무도 모른다.

## 🔴 IPv6 — fail2ban 은 이 자리를 **못 막는다** (SR-046 · 2026-08-05)

### 무엇이 문제였나 (전부 이 서버 실측)
`sshd` 는 `[::]:22` 도 듣는다. 그런데 fail2ban 이 v6 를 **한 건도 못 잡는다**:

```
fail2ban-regex '…Failed password for root from fe80::1%enp3s0 port 2 ssh2' /etc/fail2ban/filter.d/sshd.conf
  →  0 matched, 1 missed
```

`<HOST>` 정규식이 링크로컬 주소의 **존 접미사**(`%enp3s0`)를 못 읽는다. 즉 v6 경로에는
`maxretry` 도 `bantime` 도 **적용되지 않는다.**

그리고 그 상태를 **감시도 못 봤다**:

```
ip6tables -S INPUT   →  -P INPUT ACCEPT      (그것뿐이었다)
check_fail2ban ②     →  iptables(v4) 만 본다  →  초록
```

글로벌 v6 주소는 없어서 인터넷에서 직접 오지는 못한다. 그러나 이 호스트는
**OpenStack 멀티테넌트 L2** 이고 같은 세그먼트에 이웃(`fa:16:3e:*`)이 실재한다 —
그쪽에서는 **무제한 대입**이 가능했다. (`ignoreip` 사고 때 확인한 것과 같은 사실이다.)

### 조치 — 포트를 닫았다 (sshd 설정은 안 건드린다)
```
ip6tables -I INPUT 1 -p tcp --dport 22 -j DROP
  전: ssh -6 → Permission denied      후: ssh -6 → Connection timed out
  IPv4 접속 2회 성공 · 메인 200 · 컨테이너 8개 정상
```
⚠️ `ip6tables-persistent` 가 없어 **규칙이 재부팅에 사라진다.** 그래서 oneshot 유닛으로 다시 건다:

```ini
# /etc/systemd/system/re-v6-ssh-drop.service   (enabled · active/exited · 멱등 확인)
[Service]
Type=oneshot
RemainAfterExit=yes
ExecStart=/bin/sh -c "/usr/sbin/ip6tables -C INPUT -p tcp --dport 22 -j DROP 2>/dev/null \
                      || /usr/sbin/ip6tables -I INPUT 1 -p tcp --dport 22 -j DROP"
```

> **왜 `sshd_config` 를 안 고쳤나** — 사용자가 비밀번호 로그인 유지를 선택했고,
> `ListenAddress` 를 건드리는 것은 **잠길 수 있는** 변경이다(이 서버의 제1원칙: §"가장 비싼 사고").
> 방화벽 한 줄은 되돌리기가 즉시다.

### 감시에 넣었다 — `check_v6ssh` (경보 키는 **v4 와 따로**)
| 보는 것 | 경보 키 | 임계 |
|---|---|---|
| `ip6tables` INPUT 에 tcp/22 DROP 이 걸려 있는가 (**그 앞 순서까지**) | `v6ssh_rule` | 2회 연속 없으면 |
| `re-v6-ssh-drop.service` 가 **enabled** 인가 (재부팅 복구) | `v6ssh_unit` | 2회 연속 아니면 |
| 유닛이 enabled 인데 **마지막 실행이 failed** 인가 | `v6ssh_unit` | 2회 연속 |

- **`f2b_rule` 과 섞지 않는다.** 원인도 고칠 곳도 다르다(전자는 fail2ban 재시작,
  후자는 `ip6tables`/유닛). 한 키로 묶으면 한쪽의 해소가 다른 쪽을 덮어 끈다.
- **점프가 아니라 DROP 을 본다.** 정상 `ip6tables -S INPUT` 에는 fail2ban 이 만든
  v6 `f2b-sshd` 점프가 **이미 들어 있다** — 그런데 위 실측대로 아무것도 안 잡는다.
  v6 에서 "점프가 있으니 보호된다"는 **거짓**이고, 자체검사의 정상 픽스처가 그 줄을
  일부러 포함한다(가짜가 현실보다 관대하면 검사가 공허해진다).
- **이름만 맞는 규칙에 안 속는다.** 출발지가 붙은 DROP(`-s …`)·`-i lo` 전용·다른 포트·
  udp·맺힌 연결만(`--ctstate ESTABLISHED`)은 우리 보호로 **세지 않는다**.
- **`is-active` 는 보호의 증거가 아니다.** `Type=oneshot`+`RemainAfterExit=yes` 라
  부팅 때 한 번 성공하면 **규칙을 손으로 지워도 영원히 `active`(exited)** 다(실측).
  그래서 재부팅 복구의 기준은 **`is-enabled`** 이고, `inactive` 자체는 경보가 아니다
  (`ExecStop` 이 없어 stop 해도 규칙을 안 걷는다 · enabled 면 다음 부팅에 다시 건다).
- 🔴 **함정 하나를 실측으로 갈랐다.** 유닛 파일을 지우면 `is-enabled` 는
  **stdout 이 비고 rc=1**(사유는 stderr) 인데, 그것은 systemd 를 못 읽었을 때와
  **모양이 같다.** `is-active` 가 낱말을 주면(없는 유닛에도 `inactive` 를 준다)
  버스는 살아 있다는 뜻이므로 → **유닛 부재 = 경보**, 둘 다 비면 → **감시불능**.
  이 구분이 없으면 *사람이 유닛을 지운 사고*가 `logblind` 한 통에 묻힌다.
- **fail-open 은 v4 와 같다.** `ip6tables` 가 **없거나**(v6 를 안 쓰는 호스트) 실행에
  실패하면 그건 "규칙 없음"이 아니라 **감시불능**이고, 그때는 `clear_alert` 를 안 부른다.

### ⚠️ 이 조치·감시가 **못 하는 것** (없는 척하지 않는다)
- **v6 무차별 대입을 세지 못한다.** 포트를 닫았을 뿐 fail2ban 의 v6 탐지는 **여전히 0** 이다.
  규칙이 빠져 있던 동안 무슨 일이 있었는지는 `auth.log`(monitoring.md #7b)로만 안다.
- **`fail2ban` 의 v6 필터를 고친 것이 아니다.** `<HOST>` 정규식과 존 접미사 문제는 그대로다.
  v6 로 SSH 를 **열어야 하는 날**이 오면 이 조치는 못 쓰고, 그때 그 문제를 다시 풀어야 한다.
- **DROP 앞 하위 체인의 안**은 못 본다(`-j ufw6-before-input` · `-j RETURN`) → `blind_add`.
- **`sshd` 가 v6 를 정말 듣는지**는 안 본다. `ListenAddress` 를 v4 로 좁히면 규칙 없이도
  안전한데 우리는 "DROP 없음"이라 운다(오탐). 지금은 `[::]:22` 를 듣는다(실측).
- **재부팅을 실제로 해 보지는 않았다.** 유닛이 `enabled` 이고 `ExecStart` 가 멱등인 것까지
  확인했고(손으로 재실행 → 규칙 1줄 유지), 부팅 경로 자체는 다음 재부팅 때 드러난다.
- **다른 v6 포트**는 안 본다. 이 검사는 SSH 한 칸이다.
- **네이티브 `nft` 규칙은 `ip6tables -S` 에 안 보인다.** 이 서버의 백엔드는 `nf_tables` 지만
  우리가 읽는 것은 **ip6tables 호환 테이블**뿐이다 — 누군가 `nft` 로 더 높은 우선순위의
  훅에 ACCEPT 를 넣으면 우리는 그것을 못 보고 "DROP 걸려 있음"이라고 적는다.
  (v4 의 7d-② 도 같은 한계를 가진다. 오늘 이 서버에 그런 규칙은 없다.)
- **DROP 보다 앞에 `f2b-sshd` 점프가 오도록 순서가 바뀌면** 그 점프의 안을 못 보므로
  매 실행 `blind_add` 가 남는다(감시불능 한 줄이 상시 켜진다). 오늘은 DROP 이 1번이라
  해당 없다 — 순서를 바꾸는 사람이 이 문장을 보게 여기 적어 둔다.

## 남은 구멍 — `PasswordAuthentication yes`
fail2ban 은 **속도만** 늦춘다. 비밀번호 로그인이 열려 있는 한 느린 대입은 계속 가능하다.
우리는 **공개키만** 쓰고 있다(실측: 공개키 성공 443 · 비밀번호 성공 0).
`PermitRootLogin yes` 도 함께 남아 있다.

## 못 잡는 것 (추가)
- **유닛의 `ExecStart` 내용은 안 본다(CR51-3).** `is-enabled` 로 *재부팅 복구가 보장된다* 고 적었지만,
  실제로 보는 것은 **유닛 이름과 enabled 여부**뿐이다. 누가 `ExecStart` 를 빈 명령으로 바꿔 놓으면
  우리는 여전히 초록이다. (현재 유닛은 실측상 올바르다.)
