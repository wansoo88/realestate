# docs/03-build/evidence — 리뷰 실측 증적

> 소유: `re-review`. CR-009 §3 권고("서버·계산 실측의 원문을 저장소에 남겨 재현 가능하게")를
> re-review 가 먼저 이행한 것이다. G2 근거감사 원칙 6(재현성).

판정의 근거가 된 **측정 원문**을 여기 남긴다. 원장(`code-review-log.md`·`security-review-log.md`)은
결론을 적고, 이 디렉터리는 그 결론을 **다시 만들어낼 수 있는 재료**를 담는다.

## 6억캡 재감사 기준선 (지시 `2026-07-25-12-review` (B) 대비)

`ORDER 2026-07-25-10-arch` → 후속 `re-domain`(engine 6억캡 계산)·`re-data`(값) 가 끝난 뒤
**"6억캡이 실제로 실구매 가능액을 낮추는가"** 를 판정하기 위해, **변경 전에** 기준선을 떠 두었다.
변경 후에 기준선을 만들면 그건 기준선이 아니다.

### 파일

| 파일 | 내용 |
|---|---|
| `baseline_head.json` | **HEAD `213684c`**(캡 적용 전)의 실측 자금계산 결과 |
| `expected_after_cap.json` | re-review 독립 참조구현이 계산한 **캡 적용 후 기대값(정답표)** |

### 측정 조건
- 코드: `git archive HEAD` 스냅샷 (re-arch 작업트리를 건드리지 않기 위해 별도 추출)
- 규칙: `config/tax_rules.yaml` (LTV 70.0% · DSR 40.0%)
- 차주: `LoanTerms()` 기본(연 4.0% · 30년 · DTI 미적용), `PropertyFacts()` 기본
- 가정: **수도권**(6.27 대책 6억 절대한도 적용 대상), 캡 = `600,000,000원`

### 기준선 및 정답표

| 시나리오 | 현금 / 연소득 | 캡 전 최대구매가 | **캡 후 기대값** | 차이 | 캡 후 대출액 |
|---|---|---:|---:|---:|---:|
| S1 저소득·저현금 | 1억 / 5천만 | 249,200,000 | **249,200,000** | 0 | 174,438,000 |
| S2 중간 | 3억 / 1억 | 840,120,000 | **840,120,000** | 0 | 588,083,780 |
| S3 대출 6억 근처 | 5억 / 2억 | 1,411,500,000 | **1,039,010,000** | −372,490,000 | 599,992,380 |
| S4 대출 6억 초과 | 8억 / 3억 | 2,289,700,000 | **1,326,750,000** | −962,950,000 | 599,993,250 |
| S5 극단 고소득 | 10억 / 5억 | 2,877,940,000 | **1,517,780,000** | −1,360,160,000 | 599,991,199 |

> **캡 전 상태의 의미**: 현재 엔진은 절대한도 없이 **9.9억~20억 대출**을 전제로 구매가를 낸다.
> 고소득 차주 기준 실구매 가능액이 최대 **13.6억 과대 산정**된다. 이는 CHARTER §0 이 규정한
> 이 프로젝트 최대 리스크 — *틀린 근거로 수억 원짜리 매수 결정을 하게 만드는 것* — 에 정확히 해당한다.
> 10-arch 지시의 전제("6억캡 미반영이 가장 큼")는 **실측으로 확인된다.**

### (B) 판정 기준 — 이 두 가지를 모두 만족해야 PASS

1. **캡이 실제로 문다**: S3·S4·S5 의 `max_purchase` 가 위 "캡 후 기대값"과 **일치**하고,
   `loan` 이 6억을 넘지 않아야 한다.
   ⚠️ 값이 안 내려가면 **캡은 파싱만 되고 계산에 배선되지 않은 것**이다 —
   `SR4-2`(가드가 있으나 no-op) 와 **동일한 실패 유형**이므로 특히 경계한다.
   배선 지점은 `engine._limits_at()` 의 `candidates` 리스트다. 여기 들어가지 않고
   리포트·근거 문자열에만 등장하면 **no-op** 이다.
2. **하위호환**: S1·S2 는 캡이 물지 않는 구간이므로 **값이 변하면 안 된다**(0 이어야 함).
   변하면 누진밴드·스트레스DSR 도입이 기존 계산을 건드린 회귀다.

### 재현 방법
```powershell
# HEAD 스냅샷을 별도 디렉터리로 추출(작업트리 무영향)
git archive HEAD backend config | tar -x -C <임시경로>
# <임시경로>/backend 에서 config/tax_rules.yaml 로 compute_affordability 실행
```
`expected_after_cap.json` 은 `_limits_at` 의 `min(LTV, DSR)` 에 `600_000_000` 을
**세 번째 후보로 추가**한 것과 수학적으로 동일한 참조구현으로 산출했다.

### 한계 (정직하게)
- 스트레스 DSR 가산금리·6~9억 누진산식은 **아직 값이 없어**(re-data 몫) 기준선에 반영되지 않았다.
  위 정답표는 **6억 절대한도만** 적용한 값이다. 스트레스 DSR 이 들어오면 기대값은 **더 내려간다**.
  따라서 (B) 에서 실제 결과가 정답표보다 **낮으면** 스트레스DSR 기여분인지 따로 분리해 확인한다.
- 캡의 지역조건(수도권 한정)은 시나리오에서 참으로 가정했다. 비수도권에서 캡이 물면 그건 오적용이다 —
  (B) 에서 별도 확인한다.
