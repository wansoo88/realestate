## 6억캡 재감사 기준선 (지시 `2026-07-25-12-review` (B) 대비)

`ORDER 2026-07-25-10-arch` → 후속 `re-domain`(engine 6억캡 계산)·`re-data`(값) 가 끝난 뒤
**"6억캡이 실제로 실구매 가능액을 낮추는가"** 를 판정하기 위해, **변경 전에** 기준선을 떠 두었다.
변경 후에 기준선을 만들면 그건 기준선이 아니다.

### (B) 판정 기준 — 이 두 가지를 모두 만족해야 PASS

1. **캡이 실제로 문다**: S3·S4·S5 의 `max_purchase` 가 위 "캡 후 기대값"과 **일치**하고,
   `loan` 이 6억을 넘지 않아야 한다.
   ⚠️ 값이 안 내려가면 **캡은 파싱만 되고 계산에 배선되지 않은 것**이다 —
   `SR4-2`(가드가 있으나 no-op) 와 **동일한 실패 유형**이므로 특히 경계한다.
   배선 지점은 `engine._limits_at()` 의 `candidates` 리스트다. 여기 들어가지 않고
   리포트·근거 문자열에만 등장하면 **no-op** 이다.
2. **하위호환**: S1·S2 는 캡이 물지 않는 구간이므로 **값이 변하면 안 된다**(0 이어야 함).
   변하면 누진밴드·스트레스DSR 도입이 기존 계산을 건드린 회귀다.

## 사전 등록 점검표 (pre-registered) — 재감사 대상 `ORDER 2026-07-25-14-domain`

> **재감사 대상 정정**(re-pm, 2026-07-25): 대상은 10-arch 가 아니라 **14-domain** 이다.
> 10-arch(로더)는 engine 미접촉이라 캡이 계산에 들어가지 않는다. 14-domain 이 engine 에
> **6억캡 적용 + `PropertyFacts.region_group` 추가**를 한다.
> 10-arch·CR-008 정정은 `d6d1854` 로 커밋됨. **baseline `213684c` 유효성 재확인:**
> `git diff 213684c HEAD -- backend/app/domain/affordability/` → **비어 있음**(engine·models 무변경).

**구현을 보기 전에** 점검 항목을 고정한다. 결과를 본 뒤에 기준을 만들면 무엇이 나오든 합리화하게 된다.

### C1. 캡이 계산에 실제로 배선되는가 (최우선 · SR4-2 동일 실패유형)
- `engine._limits_at()` 의 `candidates` 리스트에 캡이 **후보로 들어가야** 한다.
  `min(LTV, DSR, [DTI], CAP)` 이어야 하며, 이분탐색이 이 값을 쓴다.
- ⛔ **불합격 유형**: 캡이 `evidence`·`assumptions`·리포트 문자열에만 등장하고 `candidates` 에는
  없는 경우. 숫자가 안 변하면 **파싱만 되고 계산에 안 들어간 것**이다 → `SR4-2` 와 동일.
- 검증: 정답표(위 표) 대조. S3·S4·S5 가 **정확히** 내려가야 한다.

### C2. `region_group` 기본값이 캡을 무력화하지 않는가 (두 번째 no-op 경로)
현재 생산 코드의 `PropertyFacts` 생성 지점은 **단 2곳**이다:

| 위치 | 형태 | 위험 |
|---|---|---|
| `app/api/routes.py:222` | `PropertyFacts(area_m2=body.area_m2, is_regulated_area=body.is_regulated_area, purpose=body.purpose)` | **실제 제품 경로.** 여기에 `region_group` 이 안 넘어가면 제품에선 캡이 영영 안 문다 |
| `app/domain/affordability/engine.py:143` | `prop = prop or PropertyFacts()` | 인자 생략 시 **전 기본값**. 기본이 비수도권이면 조용히 무캡 |

- ⛔ **불합격 유형**: `region_group` 이 비수도권 기본값을 갖고, 단위 테스트만 명시적으로 수도권을
  넘겨 통과하는 경우 → **테스트는 초록인데 제품은 무캡**. 가장 위험한 결말이다.
- ⚠️ **이 제품의 대상 지역은 CLAUDE.md 상 수도권 전체(서울 25구+경기+인천)** 다. 즉 사실상
  **모든 대상 매물이 수도권**이다. 따라서 캡이 꺼지는 쪽이 기본값이면 **범위상 거꾸로**다.
  안전한 기본은 "캡 적용", 비수도권이 명시적 예외여야 한다.
- 검증: `routes.py` 의 `PropertyFacts(...)` 호출 인자를 직접 읽고, `region_group` 을
  **어디서 얻는지** 확인한다. 클라이언트 요청 바디에서 온다면 C3 로 넘어간다.

### C3. `region_group` 이 클라이언트 입력이면 신뢰 문제
`AffordabilityIn` 은 이미 `is_regulated_area: bool = False` 를 **클라이언트가 보내는 값**으로 받는다.
`region_group` 이 같은 패턴이면, 사용자가 값을 바꿔 **캡을 우회하고 과대 산정된 금액**을 볼 수 있다.
- 올바른 방향: 대상 단지의 `region` (PostGIS) 에서 **서버가 판정**.
- 즉시 그렇게 못 하면, 최소한 **기본값이 수도권(캡 적용)** 이고 가정에 명시되어야 한다.
- 이건 G2(근거 감사) 사안이다 — 사용자가 스스로 근거를 유리하게 바꿀 수 있으면 근거가 아니다.

### C4. 하위호환 회귀
- S1·S2 불변(캡 미적용 구간). 변하면 회귀.
- 기존 `test_affordability.py`·`test_agents.py` 의 `PropertyFacts(area_m2=84.0)` 호출 **20여 곳**이
  새 필드 추가로 깨지지 않아야 한다(기본값 있는 필드로 추가되었는가).
- 전체 회귀 기준선: **286건 · 29 skip(needs_db) · 257 실행** (CR-009 측정).

### C5. 누진 계산 정확성
- 6~9억 누진산식이 밴드 경계(6억·9억)에서 **연속**인가. 경계 직전/직후 값이 튀면 안 된다.
- 0.5억 서브밴드 근사(±0.2%p)를 대체한 것이므로, 근사 대비 **오차가 줄었는지** 확인.

### C6. 스트레스 DSR 분리 확인
정답표는 **6억 절대한도만** 반영했다. 실제 결과가 정답표보다 더 낮으면 스트레스 DSR 기여분인지
분리해 확인한다 — 원인 불명의 추가 하락을 "캡이 잘 물었다"로 뭉뚱그리지 않는다.

### 한계 (정직하게)
- 스트레스 DSR 가산금리·6~9억 누진산식은 **아직 값이 없어**(re-data 몫) 기준선에 반영되지 않았다.
  위 정답표는 **6억 절대한도만** 적용한 값이다. 스트레스 DSR 이 들어오면 기대값은 **더 내려간다**.
  따라서 (B) 에서 실제 결과가 정답표보다 **낮으면** 스트레스DSR 기여분인지 따로 분리해 확인한다.
- 캡의 지역조건(수도권 한정)은 시나리오에서 참으로 가정했다. 비수도권에서 캡이 물면 그건 오적용이다 —
  (B) 에서 별도 확인한다.
