# 02. `finance-tax-advisor` — 세금·대출 전문가 (MVP)

> 공통 규약: [`README.md`](README.md)
> 담당 요구사항: **F2**(내 자산/대출 한도에 맞는 후보)

## 목적
"내가 **실제로** 살 수 있는 금액이 얼마인가"를 확정한다.
집값만 보고 예산을 잡으면 취득세·중개보수·이사비에서 무너진다. 그걸 다 반영한 **실구매 가능 금액**을 낸다.

## ⛔ 이 에이전트는 LLM으로 계산하지 않는다

**전부 결정론적 계산 엔진**이다. LLM은 결과를 설명하는 문장 생성에만 쓴다.

> 세율을 LLM에 물어보면 그럴듯하게 틀린다. 그리고 그 오류는 수천만 원 단위다.
> 이 에이전트에서 LLM이 숫자를 만들어내면 **즉시 G2 반려**다.

## ⚠️ 세율·규제는 코드에 박지 않는다

부동산 세제와 대출 규제는 **자주 바뀐다.** 하드코딩하면 조용히 틀린 답을 내는 시스템이 된다.

```yaml
# config/tax_rules.yaml  (버전 관리 · 출처 필수)
version: "2026-07-24"
acquisition_tax:
  - condition: { houses_owned: 1, price_max_krw: 600000000, area_max_m2: 85 }
    rate_pct: <확인 필요>
    source: "지방세법 §11"
    source_url: "https://law.go.kr/..."
    as_of: "<고시일>"
    verified_by: "위택스 계산기 대조"
```

| 규칙 | 강제 |
|---|---|
| 모든 세율·한도에 `source` + `as_of` + `source_url` | 없으면 로딩 자체를 거부 |
| `as_of`가 N개월 이상 지나면 경고 | 갱신 알림 (5단계 모니터링) |
| 위택스·국세청 계산기와 **대조 테스트** | 4단계 테스트 필수 케이스 |

> 이 문서에 구체 세율을 적지 않는 이유: **여기 적힌 숫자가 근거처럼 굳어버리기 때문이다.**
> 실제 값은 `re-data`가 공식 출처에서 가져와 `config/tax_rules.yaml`을 채운다.

## 계산 구조

### 1) 실구매 가능 금액
```
가용현금 = 보유현금 − 이사·수리 예비비
대출한도 = min(
    LTV한도  = 주택가격 × LTV비율(지역·주택수·목적별),
    DSR한도  = f(연소득, DSR상한, 금리, 만기, 기존대출 상환액),
    DTI한도  = f(연소득, DTI상한, ...)          # 적용 지역만
)
max_purchase = 해를 구한다:
    P  s.t.  P + 취득부대비용(P) ≤ 가용현금 + 대출한도(P)
```
> 대출한도가 **주택가격의 함수**이므로 단순 덧셈이 아니다. **수치해**(이분탐색)로 푼다.
> 이 구조를 놓치면 예산이 과대 산정된다.

### 2) 취득 부대비용
| 항목 | 산식 |
|---|---|
| 취득세 | 가격·주택수·면적·지역 구간별 세율 (config) |
| 지방교육세·농특세 | 취득세 부가 |
| 중개보수 | 거래금액 구간별 요율 상한 (config) |
| 등기·법무 | 정액 추정 (설정값, 추정임을 표기) |

### 3) 보유 시뮬레이션 (연간)
재산세 + 종부세(해당 시) + 관리비 추정 → **"사고 나서 매년 얼마 나가는지"**

### 4) 양도 시뮬레이션 (매도 가정)
보유기간·주택수·비과세 요건별 양도세 개략. **"지금 사면 몇 년 뒤 팔 때 얼마 남나"**
> 가정이 많아 `confidence`를 낮게 잡고, 가정 목록을 반드시 노출한다.

## 입력
`user_profile`(복호화된 자산 3종), `owned_houses`, `household_size`, 대상 지역 규제 여부,
`config/tax_rules.yaml`, 금리 가정

## 출력
```json
{
  "agent_id": "finance-tax-advisor",
  "max_purchase_krw": 850000000,
  "breakdown": {
    "own_cash_krw": 300000000, "max_loan_krw": 550000000,
    "binding_constraint": "DSR",
    "ltv_limit_pct": 70, "dsr_limit_pct": 40
  },
  "acquisition_cost_krw": { "tax": 0, "brokerage": 0, "registration": 0 },
  "holding_cost_annual_krw": { "property_tax": 0, "comprehensive_tax": 0 },
  "verdict": "예산 내 적합",
  "rationale": "가용현금 3.0억과 DSR 한도 5.5억을 합쳐 취득비용 포함 8.5억까지 가능합니다. 한도를 묶는 것은 LTV가 아니라 DSR입니다.",
  "evidence": [
    { "claim": "취득세율 X%", "source": "지방세법 §11", "as_of": "...", "source_url": "..." },
    { "claim": "DSR 상한 40%", "source": "...", "as_of": "..." }
  ],
  "assumptions": ["금리 연 4.0% · 만기 30년 원리금균등", "이사·수리 예비비 2,000만원"],
  "confidence": 0.95,
  "risks": [{ "severity": "medium",
              "detail": "실제 한도는 금융기관 심사·신용등급에 따라 달라집니다." }]
}
```

**`binding_constraint`가 이 에이전트의 진짜 가치다.** "8.5억까지 가능"보다
**"LTV가 아니라 DSR이 발목을 잡는다 → 소득을 늘리거나 기존대출을 갚으면 한도가 오른다"** 가 행동 가능한 정보다.

## 검증 포인트 (re-review)
- [ ] LLM이 금액을 생성하지 않는가 (계산 엔진 출력만 쓰는가)
- [ ] 모든 세율·한도가 `config`에서 오고 `source`·`as_of`를 갖는가
- [ ] 대출한도를 **가격의 함수**로 풀었는가 (단순 합산 아님)
- [ ] 위택스/국세청 계산기 대조 테스트가 있는가
- [ ] 자산 원본 금액이 Claude API 프롬프트에 포함되지 않는가 (`security.md` §6)
- [ ] `assumptions`가 사용자에게 노출되는가
