## 0. 결론부터 — 무엇을 막을 수 있고 무엇을 못 막는가

성공기준 ④("추천 매물의 사후 수익률이 시장 평균 초과")를 재려면 **과거 시점 T 로 돌아가
그때 알 수 있었던 것만으로 추천을 재현**해야 한다. 그게 되는지부터 답한다.

| 정보 | T 시점 재현 | 근거 |
|---|---|---|
| **실거래 가격·계약일** | **막을 수 있다** | 계약일 + 법정 신고기한 30일(`timeadjust.REPORT_LAG_DAYS`)로 경계를 긋는다. §2-A |
| **동(棟) `apt_dong`** | **막을 수 있다(마스킹 필요)** | 등기 완료 후에야 채워진다 → `registered_at > T` 인 거래는 T 시점에 **동을 몰랐다**. 뷰에서 `None` 으로 지운다. §2-B |
| **세대수 `total_households`** | **막을 필요가 없다** | 준공 시 확정되고 변하지 않는다. 상수 가정이 정당한 **유일한** 축. §2-E |
| **시장지수 `market_price_index`** | **막을 수 있다(쓰지 않는 방식으로)** | 적재값은 전 기간으로 계산돼 누출이다. 백테스트는 이 표를 **읽지 않고**, 두 시점을 **같은 방식**으로 재서 비(比)만 쓴다. §2-C |
| **해제 거래 `is_cancelled`** | **못 막는다** | `trade` 에 **`cancelled_on` 컬럼이 없다**(수집기는 이미 파싱하는데 적재에서 버린다). 언제 해제됐는지 모르니 "T 시점에 살아 있었나"를 알 수 없다. **상·하한 두 번 돌려 범위로만** 말한다. §2-D |
| **학군(학구도)** | **못 막는다** | `school_district` 는 `(source, source_ref)` 유니크라 재적재가 **덮어쓴다** — 이력이 없다. 현재 스냅샷뿐. §2-F |
| **교통·생활 인프라(POI)** | **못 막는다** | 개·폐업/개통 이력 없음. 현재 스냅샷뿐. §2-F |
| **재건축 단계** | **막을 수 있을 가능성이 있다(미확인)** | `redev_project` 에 단계별 일자 컬럼이 있다(`zone_designated_on`·`association_on` …). 채워져 있다면 T 이하 일자만 보고 그때 단계를 복원할 수 있다. **적재율 미측정**. §2-F |

### 그래서 이번 백테스트가 재는 것 / 재지 않는 것

**재는 것** — 시간에 따라 변하는 축 셋뿐이다: **가격매력 · 가격추세 · 환금성**.
현행 총점 가중치에서 이 셋의 합은 **0.45** 다(가격매력 .20 + 환금성 .15 + 가격추세 .10).

**재지 않는 것** — **학군 .20 · 교통 .20 · 인프라 .15**, 합 **0.55**.
과거 상태를 모르므로 넣으면 그 순간 결과 전체가 거짓말이 된다.

> ⚠️ **이 한 줄을 결과보다 먼저 읽어야 한다.**
> 이 백테스트는 *"우리 추천이 맞았나"* 를 재지 못한다. 재는 것은
> **"총점의 45%를 차지하는 시변 축이 초과수익을 냈나"** 다.
> 나머지 55%(입지 3축)는 **영원히 채점 대상이 아니다** — 새 데이터를 모으는 것으로도 안 된다
> (과거의 학군·상권 상태를 파는 데이터 소스가 우리에게 없다).

> ⚠️ 그리고 **지금 데이터(2024-01~)로는 그 셋 중 둘(가중치 0.35)뿐이다.**
> 가격추세는 "직전 창 대비"라 창이 하나 더 필요한데, 지금 범위로는 가능한 `T` 가 **없다**(§4-B).
> 도는 중인 2021-01 백필로도 **하락기 폴드(F1·F2)에서는 여전히 빈다** — 2020-01 이 필요하다(§4-D).

**"지금 데이터로는 제대로 못 잰다"가 정당한 결론이다.** 이 골격의 목표는 숫자를 만드는 것이
아니라 **잴 수 있는 상태를 만들고, 못 재는 부분을 못 잰다고 말하게 하는 것**이다.

## 1. 채점 단위 — 왜 "단지"가 아니라 "(단지, 면적대)" 인가

**단위(cell) = `(complex_id, area_band)`**. 면적대 경계는 `hexagon-report-data.md §2-A` 와 같다:
`<60` · `60~85` · `85~102` · `102~135` · `>135` (㎡, 전용). 새 숫자를 만들지 않는다.

단지 단위로 재면 **믹스 효과**가 수익률로 둔갑한다. 같은 단지라도 T 창에는 84㎡ 가 많이 팔리고
T+12 창에는 59㎡ 가 많이 팔리면 ₩/㎡ 중위가 오른다 — 시장이 한 푼도 안 움직여도 그렇다.
실측으로 그 크기가 크다: 최근 12개월 전체 거래의 면적대별 중위 ₩/㎡ 는
`<60` 867만원 vs `>135` 704만원 — **23.1% 차이**(`hexagon §2-A`).
믹스가 조금만 흔들려도 12개월 수익률(수 %)을 삼킨다.

부작용: 표본이 셀 단위로 쪼개져 커버리지가 떨어진다. 그 손실은 **커버리지로 보고**하고
숨기지 않는다(§4-C). 사용자는 어차피 특정 면적대를 산다.

## 2. 미래 정보 차단 (look-ahead bias) — 이 작업의 유일한 진짜 난점

### 2-A. 실거래 가시성 경계

T 시점에 **보였다고 말할 수 있는** 거래만 쓴다. 우리 `trade` 에는 **신고일 컬럼이 없다**
(MOLIT API 가 주지 않는다 — 주는 것은 계약일 `dealYear/Month/Day`, 등기일 `rgstDate`,
해제일 `cdealDay` 셋이다). 그래서 법으로 정해진 상한을 쓴다.

```
cutoff(T) = T − REPORT_LAG_DAYS(30)          # 부동산거래신고법 §3① 계약 체결일로부터 30일
as_of_view(T) = { 거래 | contract_date <= cutoff(T) }
```

**왜 `contract_date <= T` 가 아닌가** — T 당일에 계약된 건은 그날 API 에 없다. 신고에 최대
30일이 걸린다. `<= T` 로 자르면 **T 시점 어느 화면에도 없던 가격**으로 점수를 매기게 된다.

**이 경계가 완벽하지 않은 두 방향** (`timeadjust.REPORT_LAG_DAYS` 주석과 같은 사실):

| 방향 | 무슨 일이 나는가 | 위험도 |
|---|---|---|
| **아직 남는 누출** | 기한을 넘겨 낸 지각 신고. 계약일 `T−35` 인데 실제 신고가 `T+5` 였다면 우리 뷰는 넣는다 | **누출.** 지각 신고율을 우리는 재지 않았다 → 크기 [미측정] |
| **버리는 정보** | 계약일 `T−20` 인데 `T−19` 에 신고돼 T 시점에 보였던 거래를 우리는 버린다 | 안전. 정보 손실은 결과를 보수적으로 만들 뿐 부풀리지 않는다 |

**정보 손실은 감수하고 누출은 줄이는 쪽**을 고른다. 남은 지각 신고 누출은 **닫지 못했다.**
닫으려면 신고일이 있어야 하는데 원천이 주지 않는다.

> ⛔ **`registered_at <= T` 로 자르지 않는다.** 등기(`registered_at`)는 신고보다 **몇 달 뒤**
> 사건이라 이 필터는 최근 2~4개월 거래를 통째로 지운다. 게다가 저장소가 이미 실측한 대로
> 같은 (단지,면적,계약월) 안에서 **미등기가 등기보다 +0.5~2.2% 비싸다**(migration 015 주석)
> — 등기된 것만 남기면 **싼 쪽만 골라 남기는** 선택편향이 된다. 누출을 막으려다 편향을 넣는다.

### 2-B. `apt_dong` — 놓치기 쉬운 실제 누출 경로

`apt_dong` 은 **등기가 끝난 뒤에야 채워진다**(`valuation/models.py::DONG_PERIOD_MONTHS` 주석의
실측: 등기일 있는 거래 86.3% 보유 vs 등기 전 2.0%). 그러므로 T 시점에는

* `contract_date <= cutoff(T)` 라 **거래는 보였지만**
* `registered_at` 이 없거나 `> T` 면 그 거래의 **동은 몰랐다**.

그래서 as-of 뷰는 그런 거래의 `apt_dong` 을 **`None` 으로 지운다**. `registered_at` 자체도
`> T` 면 지운다(방어적 — 하위 계산이 실수로 쓰지 못하게).

지금 채점 지표는 동을 쓰지 않는다. 그래도 뷰 단계에서 막는 이유는, 나중에 누가 동별 축을
넣을 때 **뷰를 고치지 않고도 자동으로 안전하기** 때문이다. 누출 방지는 사용처가 아니라
**입구**에 두어야 한다.

### 2-C. 시장지수 — 적재값을 읽지 않는다

`market_price_index` 는 세 겹으로 누출이다:

1. 지수는 `(complex_id, round(area))` 그룹의 **평균을 뺀 잔차**로 계산한다. 그 그룹 평균은
   **전 기간**(T 이후 포함) 거래로 만들어졌다.
2. "2개월 이상 거래한 그룹만" 이라는 자격 조건도 T 이후 거래로 충족될 수 있다.
3. `is_complete` 플래그는 배치 실행일(`as_of`)로 계산됐다 — T 의 달력이 아니다.

**대책: 백테스트는 이 표를 읽지 않는다.** 대신

* 가격 수준은 **두 시점을 똑같은 방법으로** 잰다 — 각 셀의 **12개월 창 ₩/㎡ 중위**.
* 수익률은 그 둘의 **비**다. 두 창의 구성 방식이 같으므로 시점 보정이 필요 없다.

**대가(정직하게 적는다)**: 12개월 후행 창의 중위는 창 중앙(≈ 6개월 전) 가격에 가깝다
(`timeadjust` 실측: 12개월창 평균 시점 5.8개월 전). 그래서 우리가 "T→T+12 수익률"이라 부르는
값은 실제로는 **T−6개월 → T+6개월** 구간의 변화다. **경과 시간은 정확히 12개월**이므로
수익률의 크기는 편향되지 않지만, **6개월 평활·지연**이 들어간다. 급반전 국면에서 둔해진다.

### 2-D. 해제 거래 — 못 막는다. 범위로 말한다

T 시점 정확한 규칙은 `is_cancelled = false OR cancelled_on > T` 인데,
**`trade` 테이블에 `cancelled_on` 컬럼이 없다.**

> `app/ingest/molit.py:219` 는 `cdealDay` 를 이미 파싱해 `MolitTrade.cancelled_on` 에 담고,
> `app/ingest/loader.py:310` 은 그 값을 SQL 파라미터에까지 넣는다. 그런데
> `_upsert_trade` 의 INSERT/UPDATE 컬럼 목록에 그 이름이 **없다** — 값이 조용히 버려진다.
> 즉 **수집은 되고 있고 저장만 안 된다.** (마이그레이션 017 로 컬럼을 추가하고 재적재하면
> 이 누출은 닫힌다. 이번 범위 밖 — DB 쓰기 금지.)

그래서 두 정책을 **둘 다 돌려 상·하한으로** 본다:

| 정책 | 규칙 | 성질 |
|---|---|---|
| `exclude_final` (기본) | `NOT is_cancelled` — **운영 코드와 동일** | **누출.** 사후 확정된 해제여부를 T 시점에 쓴다. 표본을 사후 지식으로 청소한 셈 |
| `include_all` | 해제 여부를 보지 않는다 | T 이전에 이미 해제된 건까지 넣는다 — 과다 포함 |
| `exclude_known_at` | `cancelled_on` 필요. 없으면 **예외로 멈춘다** | 정확. 017 이후에 쓸 자리. 지금은 못 쓴다 |

**판정 규칙**: 두 정책의 결론이 갈리면 **결론을 내지 않는다.** 5.4% 가 해제 거래이므로
(hexagon §1) 뒤집힐 여지가 실재한다. 기본을 `exclude_final` 로 둔 이유는 **운영 파이프라인이
실제로 그렇게 계산하기 때문**이다 — 우리가 채점하려는 대상은 이상적인 추천기가 아니라
**우리가 돌리는 그 코드**다.

### 2-E. 세대수 — 상수 가정이 정당한 유일한 축

`complex.total_households` 는 현재 스냅샷이다. 그래도 상수로 쓴다. 준공 시 확정되고 이후
변하지 않기 때문이다(재건축 완료로 바뀌지만, 그 단지는 멸실 기간 동안 거래가 없어 애초에
후보 유니버스에 들어오지 않는다). **한 축만은 "상수 가정"이 근거를 가진다.**

⚠️ 남는 구멍 하나: T 이후 준공된 단지는 T 시점에 존재하지 않았다. 우리 뷰는 계약일로만
자르므로, T 이전 거래가 없는 단지는 자동으로 유니버스에서 빠진다(가격 표본 미달).
**분양권 거래가 `trade` 에 섞여 있다면** 준공 전 단지가 후보가 될 수 있다 — 이 경우
"T 시점에 살 수 없던 물건"이 후보가 된다. `trade_type` 은 중개/직거래뿐이라
분양권을 식별할 칸이 없다 [미확인]. **한계로 적어 둔다.**

### 2-F. 입지 3축 — 제외한다. 그 이유와, 제외의 대가

| 축 | 과거 상태를 아는가 | 처리 |
|---|---|---|
| 학군(학구도) | **모른다.** `school_district` 는 `(source, source_ref)` 유니크 → 연 2회 재배포분이 **덮어쓴다**. `as_of` 컬럼이 있지만 한 행에 하나뿐이라 이력이 아니다 | **제외** |
| 교통(역세권) | **모른다.** 역 개통일 컬럼 없음. GTX·신설역이 언제 생겼는지 우리 DB 는 모른다 | **제외** |
| 생활 인프라(POI) | **모른다.** 개·폐업 이력 없음 | **제외** |
| 재건축 단계 | **알 수 있을지 모른다.** `redev_project` 에 `zone_designated_on`·`committee_on`·`association_on`·`implementation_on` … 단계 일자가 있다. 채워져 있다면 `일자 <= T` 인 마지막 단계로 T 시점 단계를 복원 가능 | **이번엔 제외** (적재율 [미측정]. 다음 라운드에서 먼저 재고 결정) |

**제외의 대가를 명시한다.** 세 가지 선택지가 있었고 왜 "제외"인지:

* **(가) 제외** ← 채택. 결과가 좁아지지만 **거짓말이 아니다**.
* (나) 현재 스냅샷을 상수로 가정 — 학원가·상권·역은 실제로 바뀐다. 게다가 편향의 방향이
  **나쁜 쪽**이다: 지금 인프라가 좋은 곳은 그동안 좋아졌을 확률이 높고, 그 개선이 곧
  가격 상승의 원인이다. 즉 **결과가 "입지 축이 잘 맞췄다"로 기울도록 체계적으로 부풀려진다.**
  자기 채점 도구가 자기에게 유리하게 틀리는 것은 가장 나쁜 형태의 오류다.
* (다) 별도 표기(넣되 "누출 포함" 라벨) — 라벨은 결국 떨어져 나간다. 숫자만 인용되는 자리
  (요약·프롬프트·발췌)가 이 저장소에 이미 여럿 있다.

## 3. 채점 지표

### 3-A. 실현 수익률

셀 `c` 의 시점 `A` 가격:

```
ppm(c, A) = median{ price_krw / area_m2 | 거래 ∈ as_of_view(A),
                    complex = c.complex, band = c.band,
                    cutoff(A) − W개월 < contract_date <= cutoff(A) }
            (표본 >= MIN_TRADES_PER_ENDPOINT, 아니면 '측정 불가')
W = WINDOW_MONTHS = 12,  MIN_TRADES_PER_ENDPOINT = 5
```

```
ret(c) = ppm(c, T+H) / ppm(c, T) − 1        H = HORIZON_MONTHS = 12
```

양 끝을 **같은 함수**로 만든다. 한쪽만 신고 지연을 빼면 경과 시간이 12개월이 아니게 된다.

`MIN_TRADES_PER_ENDPOINT = 5` 는 `valuation/models.MIN_SAMPLE` 과 같은 값이다 — 이 저장소가
"숫자를 화면에 올려도 된다"고 정한 하한을 백테스트에서 낮추지 않는다.

### 3-B. 비교 기준(benchmark) — 두 개를 함께 낸다

성공기준 ④의 "시장 평균"이 무엇인지 문서 어디에도 정의가 없다. 여기서 정의한다.
**한 개로는 안 된다** — 두 질문이 다르고, 하나만 고르면 반드시 오해가 생긴다.

| 이름 | 정의 | 답하는 질문 | 왜 필요한가 |
|---|---|---|---|
| **B1 시장 중위** | 유니버스 전체 셀의 `ret` **중위** (셀 **동일가중**) | "아무 셀이나 골랐을 때보다 나았나" | 성공기준 ④의 문자 그대로. 사용자는 한 채를 산다 — 거래액 가중 포트폴리오가 아니라 **무작위 한 채**가 올바른 대조군이다 |
| **B2 동종 중위** | 같은 **(시군구, 면적대)** 셀들의 `ret` 중위 (동일가중, 피어 `>= MIN_PEER_CELLS(10)`) | "지역·평형 선택 효과를 빼고도 단지를 잘 골랐나" | B1 만 보면 "강남을 골랐다"와 "강남에서 잘 골랐다"가 섞인다. 둘은 완전히 다른 능력이고, 우리 데이터가 뒷받침하는 것은 후자 쪽이다 |

```
excess1(c) = ret(c) − B1
excess2(c) = ret(c) − B2(시군구(c), band(c))       # 피어 수 미달이면 정의하지 않는다
```

**왜 평균이 아니라 중위인가** — 부동산 수익률은 꼬리가 두껍고, 저장소의 다른 통계도 전부
중위를 쓴다. 한 곳에서만 평균을 쓰면 같은 데이터에 두 진실이 생긴다.

**왜 "전체 평균"(수도권 전 거래 평균) 을 쓰지 않는가** — 그건 거래가 많은 지역·평형에
가중된 값이라, 우리 추천이 어디를 골랐든 **그 지역의 거래량**이 답을 좌우한다.
"내가 한 채 샀을 때의 대안"과 무관한 숫자다.

**⚠️ 벤치마크 유니버스 = 후보 유니버스.** B1·B2 는 반드시 **후보가 될 수 있었던 셀들**
(= T 시점 가격이 측정된 셀)로만 만든다. 다른 모집단과 비교하면 채점이 무의미해진다.

### 3-C. 무작위 대조군 — 이게 없으면 N=30 의 숫자는 못 읽는다

상위 N 의 `median(excess1)` 이 `+1.2%p` 라는 값 하나로는 아무 말도 못 한다. 표본 30개의
중위는 그 정도로 흔들린다. 그래서 **같은 유니버스에서 무작위로 N 개를 뽑는 일을 K 번
반복**(고정 시드)해 `median(excess1)` 의 분포를 만들고, 실제 상위 N 이 그 분포의 **몇 번째
백분위**인지 보고한다.

* 무작위 표본도 **점수가 매겨진 셀 풀**에서 뽑고, **같은 측정 탈락 규칙**을 적용한다.
  그러지 않으면 대조군만 측정률이 높아져 비교가 깨진다.
* `K = 1000`, 시드 고정 → 같은 입력에 같은 결과.

읽는 법: **백분위 95 이상이 아니면 "우연과 구별되지 않는다".** 이 문턱은 통계 관행이지
우리가 잰 값이 아니다 — 그래서 문턱으로 판정을 자동 출력하지 않고 **백분위 값을 그대로**
내보낸다. 판정은 사람이 한다.

### 3-D. 생존 편향 — 어떻게 다루는가

T+12 창에 거래가 없는 셀은 `ret` 이 없다. 그냥 빼면 **"안 팔린 물건"이 통계에서 사라진다.**
그리고 안 팔린 것은 무작위가 아니다 — 환금성이 나쁜 셀이 정확히 우리가 경고해야 할 대상이다.

**세 가지를 동시에 한다.**

1. **커버리지를 항상 보고한다.** 상위 N 의 측정률과 유니버스 전체의 측정률을 **나란히**.
   `top_measured_rate < universe_measured_rate` 이면 그 자체가 결과다 —
   *"우리 추천은 덜 팔리는 셀로 쏠린다"*. 이건 초과수익보다 중요할 수 있다.
2. **주 지표는 측정된 것만으로** 낸다(`unmeasured_policy = drop`). 없는 수익률을 지어내지 않는다.
3. **민감도**로 `unmeasured_policy = benchmark` 를 함께 낸다 — 미측정 셀에 B1 을 그대로
   부여(초과 0)한다. "시장만큼 움직였다"는 무정보 가정이고, **희석 방향**이라
   보수적이다. 두 값이 갈리면 결론을 내리지 않는다.
4. **하드 가드**: 상위 N 의 측정률이 `MIN_MEASURED_RATE_PCT(70%)` 미만이면 그 폴드는
   `low_coverage` 경고를 달고, **표제 숫자로 인용하지 못한다**(리포트에 그렇게 적힌다).

> ⚠️ 이 처리로도 생존 편향이 **없어지지는 않는다.** 없어지지 않는다는 사실을 숫자로
> 드러낼 뿐이다. 완전히 풀려면 "팔리지 않은 것의 가치"를 알아야 하는데 그건 호가가
> 있어야 하고, `listing` 은 0행이다.

| 필드 | 뜻 |
|---|---|
| `universe_size` / `scored_size` | 후보가 된 셀 수 / 그중 점수가 나온 셀 수 |

## 4. 폴드(fold) — 하락기가 없으면 채점이 아니다

### 4-A. 폴드 정의 — 요구 데이터 범위가 **두 가지**다

`FoldSpec(as_of=T, horizon_months=12, window_months=12)`. 여러 개를 돌린다.

| 무엇까지 재는가 | 필요한 계약일 범위 | 폭(기본값 기준) |
|---|---|---|
| 가격매력 · 환금성만 | `cutoff(T) − W` ~ `cutoff(T+H)` | **W + H = 24개월** + 30일 |
| **가격추세까지** | `cutoff(T−W) − W` ~ `cutoff(T+H)` | **2W + H = 36개월** + 30일 |

가격추세는 "직전 창 대비"라 **창이 하나 더** 필요하다. 이 차이가 백필 계획에 그대로 물린다(§4-D).
`FoldSpec.required_contract_range(include_prior=…)` 가 두 값을 다 내고, 실행기가 둘 다 로그에 찍는다.

### 4-B. 지금 데이터로 가능한 폴드 (2024-01 ~ 2026-07)

* 가장 늦은 T: `cutoff(T+12) <= 2026-07-25` → **`T <= 2025-07-25`**
* 가장 이른 T (**추세 제외**): `cutoff(T) − 12개월 >= 2024-01-01` → **`T >= 2025-01-31`**
* 가장 이른 T (**추세 포함**): `cutoff(T−12) − 12개월 >= 2024-01-01` → `T >= 2026-01-31`
  → **가능한 T 가 없다.**

→ **T ∈ [2025-01-31, 2025-07-25]. 겹치지 않는 폴드는 사실상 1개.**
그리고 **그 폴드에서는 가격추세 축이 아예 산출되지 않는다** — 지금 데이터로 잴 수 있는 것은
가격매력·환금성 둘뿐이고, 이는 현행 총점 가중치의 **0.35 / 1.00** 이다.
게다가 그 구간은 **전부 상승기**다(`timeadjust` 적재값: 서울 2025-01 → 2026-05 **+16.5%**).

### 4-C. ⚠️ 못 박아 둔다 — 상승기만으로 채점하면 무의미하다

상승장에서는 **아무거나 사도 오른다.** 그 구간에서 "상위 N 의 수익률 +18%" 는 아무 뜻이
없고, 초과수익(B1 대비)조차 상승장에서만 통하는 특성(예: 고가·소형 편향)을 잡아낸 것일 수
있다. 그 점수를 하락장에 쓰면 **정확히 반대로 작동한다.**

**규칙**:

> **하락기 폴드(B1 < 0)가 최소 1개 포함되지 않은 백테스트 결과는
> "검증됨"이라고 부르지 않는다.** 리포트 `verdict` 가 `rising_only` 로 나오고,
> 그 값은 총점 가중치 교정(§6)의 입력으로 **쓰지 못한다.**

이 규칙은 코드로도 강제한다(`engine.summarize` → `verdict`).

### 4-D. 백필 이후의 폴드 계획 — ⚠️ **지금 도는 백필(2021-01~)로는 부족하다**

서버에서 2021~2023 백필이 끝나면 T 를 반년 간격으로 잡는다. 국면 라벨은 실행 후 B1 부호로
정해지지만, 예상 구간은 다음과 같다(`enhancement-research §B`: 2021 정점 → 2022~23 하락 →
2024~ 회복). **필요 시작월**은 §4-A 의 두 범위를 그대로 계산한 값이다.

| 폴드 | T | T+12 | 예상 국면 | 필요(추세 제외) | 필요(추세 포함) | 2021-01 백필로 |
|---|---|---|---|---|---|---|
| F1 | 2022-01-31 | 2023-01 | **하락** ← 필수 | 2021-01-01 | **2020-01-01** | 추세 축 없음 |
| F2 | 2022-07-31 | 2023-07 | **하락** ← 필수 | 2021-07-01 | **2020-07-01** | 추세 축 없음 |
| F3 | 2023-01-31 | 2024-01 | 하락 말기~바닥 | 2022-01-01 | 2021-01-01 | ✅ 3축 전부 |
| F4 | 2023-07-31 | 2024-07 | 회복 | 2022-07-01 | 2021-07-01 | ✅ |
| F5 | 2024-01-31 | 2025-01 | 상승 | 2023-01-01 | 2022-01-01 | ✅ |
| F6 | 2024-07-31 | 2025-07 | 상승 | 2023-07-01 | 2022-07-01 | ✅ |
| F7 | 2025-01-31 | 2026-01 | 상승 | 2024-01-01 | 2023-01-01 | ✅ |

> ⚠️ **하락기 폴드 둘(F1·F2)에서만 하필 가격추세 축이 빠진다.** 그리고 가격추세야말로
> 국면별로 부호가 뒤집힐지(모멘텀 vs 평균회귀) **가장 궁금한 축**이다(§6-3).
> 하락기에 그 축을 못 재면 교정의 핵심 질문에 답을 못 한다.
>
> **권고: 2020-01~2020-12 를 추가로 백필한다.** 12개월 × 66 시군구 ≈ 800 요청
> (기존 수집이 통과한 2,000 요청보다 작다), 요청 간격 0.5초 기준 **약 10분**.
> 대안은 F1·F2 를 2축(가격매력·환금성)으로 돌리고 가중치를 재정규화하는 것인데,
> **폴드마다 축 구성이 달라져 폴드 간 비교가 성립하지 않는다.**

* 폴드끼리 창이 겹치므로 **독립이 아니다.** 폴드 수를 표본 수처럼 쓰면 안 된다.
  집계는 **폴드 동일가중 중위**로 하고(데이터가 많은 시기가 지배하지 않게), 폴드별 값을
  **항상 함께** 낸다.
* ⚠️ 2021~2022 구간은 `apt_dong` 이 **거의 없다**(`enhancement-research §B` 실측:
  2022-01 이전 0/50). 동 축은 그 폴드에서 원천적으로 불가 — 어차피 §2-F 로 제외했다.

## 5. 구조 — 어디에 무엇이 있는가

```
backend/app/domain/backtest/
    models.py       면적대 · BacktestTrade · AsOfCell · PricePoint · CellOutcome · 폴드/결과 모델
    asof.py         ★ as-of 뷰. 누출 차단이 전부 여기 있다 (cutoff · apt_dong 마스킹 · 해제 정책)
    outcome.py      가격 시점(ppm) · 실현 수익률 · 벤치마크 · 생존 편향 정책
    collect.py      ★ 스트리밍 집계. **행을 쌓지 않는 것**이 전부 여기 있다 (§5-1)
    scorers.py      점수 함수들(전부 as-of 셀만 본다) + 무작위/상수 대조군
    engine.py       폴드 실행 · 무작위 대조군 · 국면 라벨 · 집계/판정
    repository.py   Protocol — 도메인은 SQL 을 모른다
backend/scripts/run_backtest.py     실행기(리포지토리 구현 + 리포트 출력)
```

**규칙**

1. `app/domain/backtest/**` 는 **SQL 도 엔진도 모른다.** 전부 순수 함수 + 데이터클래스.
2. 리포지토리는 **as-of 필터를 걸지 않는다.** 원본 거래를 그대로 준다.
   자르는 곳은 `asof.py` **한 곳**이다. 두 곳에서 자르면 한쪽만 고쳐지는 날이 온다.
3. 리포지토리는 `is_cancelled` 로도 거르지 않는다(해제 정책은 도메인이 정한다).
4. 점수 함수는 `AsOfCell` 만 본다. 원본 거래를 받지 않는다 —
   **누출을 하고 싶어도 손이 닿지 않게** 타입으로 막는다.
5. **거래를 리스트로 접지 않는다.** 소비는 `collect.FoldCollector.feed` 를 통해서만 —
   아래 §5-1.

### 5-1. 실행기의 메모리 상한 — 왜 이렇게 고쳤나 (CR49-3)

리포지토리는 `Iterator` 로 스트리밍을 **약속**한다. 그런데 첫 판의 실행기는
`trades = list(repo.trades_for_backtest(...))` 로 그 약속을 소비 쪽에서 무효로 만들었다.

**실측 (2026-08-05 · 2021~2023 백필 완료 후)**

| 항목 | 값 |
|---|---|
| `trade` 행 수 | **1,076,262** (백필 전 611,518) |
| §8 첫 실행 예시(`--as-of 2025-01-31`)의 필요 범위 | 2023-01-01 ~ 2026-01-01 = **613,228행** |
| `BacktestTrade` 1행 | **383 B** (`tracemalloc`) |
| 그 목록의 힙 | **≈ 235 MB** |
| 서버 가용 메모리 | **261 MB** (총 957MB · 스왑 2G 중 698MB 사용 중) |

즉 **폴드 하나가 가용 메모리의 90%** 였다. API 컨테이너(`mem_limit 192m`)와 postgres 가
같은 상자에 산다 — 하드 OOM 이 아니어도 스래싱이면 이미 사고다.

> ⚠️ **함정**: `list()` 만 벗기면 안 됐다. `trades` 는 폴드마다 다시 순회되고 세대수 조회도
> 같은 집합을 쓰므로, 제너레이터를 그대로 넘기면 **두 번째 순회에서 조용히 0행**이 된다
> (예외도 안 난다 — 빈 유니버스로 리포트가 나온다). 그래서 고친 것은 소비 **방식**이다.
>
> **그리고 그 함정을 코드로 닫았다**(CR50-3). 소비 방식만 바꿨을 때는 실행기와
> `engine.run_backtest` 만 안전했을 뿐, 공개 API 짝(`build_cells` + `build_outcomes`)에
> 함정이 **그대로 살아 있었다** — 리뷰어가 `measured 0/5 · 예외 없음`으로 재현했다.
> "운영 경로엔 없다"는 대책이 아니다. 지금은 네 자리가 예외로 죽는다:
>
> | 실수 | 예전 | 지금 |
> |---|---|---|
> | `build_cells(gen)` → `build_outcomes(gen)` | 두 번째가 조용히 0행 · 리포트는 나온다 | `TypeError` — 두 함수는 **다시 훑을 수 있는** 것만 받는다(`iter(x) is x` 면 거부) |
> | `feed` 재호출 | `rows_seen`·`sample_size` **조용히 2배**(환금성 축의 분자다) | `StreamAlreadyConsumed` |
> | 같은 제너레이터를 수집기 둘에 | 두 번째가 0행 | `StreamAlreadyConsumed`. ⚠️ 약한 참조를 못 거는 이터레이터(`list_iterator`·`map`·`chain`)는 못 잡는다 — 그 구멍은 윗줄의 `TypeError` 가 앞에서 막는다 |
> | 같은 `FoldSpec` 두 번 | 뒤 창이 채워지되 안 읽힌다 · 표본만 2배 | `ValueError` |
>
> 변이 시험: 이 가드 넷을 지우면 `TestSecondPassTrap` 의 **5검사**가 죽는다.

**검토한 안과 판정**

| 안 | 판정 | 이유 |
|---|---|---|
| ① 폴드마다 그 폴드 범위만 다시 조회 | **버렸다** | 창을 좁혀도 **폴드 1개가 이미 235MB** 다(위 실측이 폴드 1개짜리다). 게다가 폴드 수만큼 `mem_limit 192MB` db 컨테이너를 다시 훑는다 |
| ② **한 번 순회하며 전 폴드 셀을 동시 집계** | **채택** | DB 1회 통과. 폴드가 늘어도 **행** 보유량은 그대로다(느는 것은 값 통뿐) |
| ③ 행 자체를 줄이기(SQL 에서 미리 집계) | **버렸다** | 창 경계·해제 정책·`apt_dong` 마스킹이 SQL 로 내려가면 **자르는 곳이 두 곳**이 된다 — 위 규칙 2를 정면으로 어긴다. 한쪽만 고쳐지는 날 백테스트 전체가 조용히 거짓이 된다 |
| ④ 실행 전 `count(*)` 로 재고 임계 초과면 중단 | **부분 채택** | 이것만으로는 "안 돌린다"일 뿐 **못 돌린다**는 그대로다. ②를 하고 그 위에 표본 상한을 얹어 폭주만 막는다 |

**채택안이 지키는 두 상한** — 둘 다 테스트가 단언한다(`TestStreamingMemoryBound`).

| 상한 | 값 | 어떻게 확인하나 |
|---|---|---|
| **순간 보유 행 수** | **2 × `chunk_rows`** = **10,000행** (≈ 2.8MB) | `weakref.finalize` 로 살아 있는 `BacktestTrade` 수를 세어 peak 을 단언. 코드도 스스로 `peak_live_rows`(청크 + 뷰)로 재고 그 값을 로그에 찍는다. 변이(청크 상한 제거)로 3검사가 죽는다 |
| **누적 표본 수** | `max_samples` = **2,000,000** | 넘으면 `SampleLimitExceeded` 로 멈춘다. 변이(raise 제거)로 1검사가 죽는다 |

> ⚠️ **왜 `chunk_rows` 가 아니라 그 2배인가 (CR50-1 정정).** 순간에 살아 있는 것은 청크
> 하나와 **그 청크의 as-of 뷰** 하나다. 뷰는 원본을 가리키는 것이 원칙이지만,
> **T 시점에 몰랐던 칸(`apt_dong`·미래 날짜)을 지우는 행은 `dataclasses.replace()` 사본**이
> 된다(§2-B). 운영 `apt_dong` 보유율이 **77~93%**(`erd §0`)이므로 **운영에서는 거의 모든 행이
> 사본**이고, 그래서 행 수가 정확히 2배가 된다. 리뷰어가 `gc` 전수로 잰 값도 같다
> (chunk 250 → `apt_dong=None` 250 · 운영 모양 **500**).
>
> **바이트로는 2배가 아니다** — 사본이 문자열·날짜 객체를 원본과 공유한다.
> 실측(2026-08-05 · `tracemalloc` · 5,000행 청크 하나의 뷰를 만들며 잰 증가분):
>
> | 청크의 모양 | 뷰가 더 먹은 양 | |
> |---|---:|---|
> | `apt_dong=None`(옛 픽스처) | **44 B/행** | 목록 슬롯만 — **사본 0** |
> | `apt_dong='101'` + 미등기(**운영 모양**) | **181 B/행** | 사본 5,000 |
>
> → 청크 1.9MB(383B/행) + 뷰 0.9MB = **약 2.8MB**.
>
> ⛔ **그리고 이 상한을 재던 검사가 그 축에서 공허했다.** 픽스처(`tracked_stream`)가
> `apt_dong`·`registered_at` 을 안 심어 **마스킹 경로를 한 번도 안 지났고**, 카운터는
> 스트림이 만든 **원본에만** `finalize` 를 걸어 사본을 한 개도 못 셌다. 지금은 픽스처가
> 운영 모양이고, 카운터가 `BacktestTrade` 하위형을 써서 `replace()` **사본까지 센다**
> (`dataclasses.replace` 는 `obj.__class__(...)` 를 부른다). 변이(마스킹 제거)로 이 절의
> 검사가 **4건 더** 죽는다(전엔 0건).

`max_samples` 근거: 표본 하나는 `array('d')` 안에서 8B, 버킷(셀×시점) 하나의 부대비용은
dict 항목+array 객체 ≈ 150B. 200만 표본 ≈ 값 16MB + 버킷 40MB 안팎 = **약 55MB**(가용의 1/5).
첫 실행 예시는 창 셋이 겹치지 않아 행당 표본 1개 이하 → **약 61만 표본**으로 상한의 1/3 이다.

**고친 뒤 실측** (`tracemalloc` · 613,228행 · 단지 20,000 · 폴드 1개 · DB 없이 행을 그대로 생성)

| | 행의 모양 | 보유 | peak | 순간 보유 행 |
|---|---|---:|---:|---:|
| 옛 `list(...)` | `apt_dong` 없음 (224 B/행) | 131.1 MB | 131.1 MB | **613,228** |
| `FoldCollector` | `apt_dong` 없음 | **22.9 MB** | **24.5 MB** | **10,000** |
| `FoldCollector` | **운영 모양**(`apt_dong` 보유 · 미등기 · 285 B/행) | **22.9 MB** | **25.4 MB** | **10,000** |

**행 보유가 613,228 → 10,000 으로 고정됐다**(데이터가 늘어도 이 숫자는 그대로다).
남은 22.9MB 는 값 통(표본 613,228개 × 8B ≈ 4.7MB)과 버킷 부대비용이며 `max_samples` 가 덮는다.
운영 모양과 옛 모양의 차이는 **peak 0.9MB**(= 청크 5,000행의 사본 몫)뿐이다 — 위 상한 표와 같은 값.

※ 리뷰어가 잰 운영 데이터 **383 B/행**으로 환산하면 옛 방식은 **≈235 MB** 로, 리뷰어 실측과
   같은 자리다. 합성 행이 그보다 가벼운 것은 문자열을 공유하기 때문이다.
※ 2026-08-05 재측정. 앞선 판의 `21.8 / 23.2 MB · 순간 5,000` 은 **as-of 뷰를 안 센 값**이라
   갈아 끼웠다(CR50-1). `옛 list(...)` 행만 그때 값 그대로다 — 운영 모양으로 다시 재려면
   613,228행을 실제로 올려야 하는데 그건 이 라운드에 하지 않았다. 그 행의 결론(≈235MB)은
   리뷰어 실측(383 B/행)이 따로 뒷받침한다.

그리고 회귀 방지로, 실행기 소스에 `list(...trades_for_backtest...)` 가 다시 나타나면
AST 검사가 붉어진다(`test_runner_never_materialises_the_trade_stream`).

## 6. 가중치 교정 — 이번 범위 밖. 방법만 적어 둔다

**지금 하지 않는 이유**: 잴 수 있는 상태가 아직 없고(§4-C: 하락기 폴드 부재),
교정 가능한 축이 6개 중 3개뿐이다(§0). 저울을 못 믿는 상태에서 추를 옮기면
**틀린 저울을 정밀하게 만드는 일**이 된다.

**다음 라운드 방법**(이 순서대로):

1. **선결**: 2021~2023 백필 완료 → 하락기 폴드 확보(§4-D). `verdict != rising_only` 확인.
2. **축 단독 실행**: 가격매력·가격추세·환금성 **각각 단독 스코어러**로 전 폴드를 돌린다.
   축 하나가 무작위 대조군을 못 이기면(백분위 < 95) **그 축은 총점에서 빼는 것**이 먼저다.
   가중치 조정이 아니라 **제거**가 1차 행동이다.
3. **부호 확인**: 특히 **가격추세**. `hexagon §8` 이 이미 "비단조"라 적었다 — 많이 오른 것이
   더 오르는지(모멘텀) 덜 오르는지(평균회귀)를 **국면별로** 본다. 상승기와 하락기에서 부호가
   뒤집히면 **고정 가중치로는 쓸 수 없다**는 결론이 나온다. 그 결론도 결과다.
4. **가중치 탐색은 마지막**, 그리고 **홀드아웃으로만**: 폴드를 학습/검증으로 나눠
   (예: F1~F4 로 정하고 F5~F7 로 확인) 격자 탐색. 전 폴드로 맞춘 가중치는
   **자기 자신에게 맞춘 것**이라 다음 12개월과 무관하다.
5. **적용 조건**: 홀드아웃 폴드에서도 무작위 대조군을 넘을 때만 교체하고,
   **교체 시점·근거 폴드·측정값을 `hexagon-report-data.md §8` 에 적어** 휴리스틱 딱지를 뗀다.
6. 그때까지 §8 의 문장(**"설계 휴리스틱이며 실측 근거 없음"**)은 그대로 둔다.

### 7-13-B. 드라이버 버퍼 — `chunk_rows` 가 덮지 못하는 몫 (CR50-2)

`chunk_rows` 는 **파이썬 도메인 객체**(`BacktestTrade`)의 상한이다. 그 앞단에 psycopg 가 있다.

* **예전 상태**: `conn.execute(...)` 에 `stream_results` 가 **없었다**(저장소 전체 검색 0건).
  SQLAlchemy 2.0.51 + psycopg 3.2.3 의 기본은 **클라이언트 커서**라, `execute()` 가 돌아오는
  순간 그 질의 결과 **전부**가 클라이언트 메모리에 있다. 질의는 시군구 단위
  (`left(c.region_code,:plen)=:region`)이므로 실제 상한이 *"가장 큰 시군구의 행 수"* 였다.
  크기 추정: 613,228행 / 거래 있는 시군구 82개 → 평균 ≈7.5천행, 편중을 감안해 ≈3만행
  ≈ **11MB**(383B/행 환산). **이 값은 [미측정]** — 리뷰어 추정이고 나도 재지 않았다.
  235MB 가 아니므로 사고는 아니었지만, "상한"이라는 말이 참이 아니었다.
* **지금**: 거래 질의에 `execution_options={"stream_results": True, "max_row_buffer": chunk_rows}`
  를 준다 → **서버측 커서**로 바뀌고 드라이버가 한 번에 쥐는 것은 `--chunk-rows` 행뿐이다.
  버퍼 크기를 수집기 청크와 **같은 숫자**로 맞춘 이유는 상한이 두 개가 되지 않게 하기 위해서다
  (검사가 `stream_rows=chunk_rows` 를 소스에서 직접 확인한다).
  `SET statement_timeout = '120s'` 는 FETCH 마다 따로 걸리므로 가드는 유지된다.

⚠️ **남은 것 — 정직하게 적는다.**

| | 상태 |
|---|---|
| `stream_results` 전환을 **운영 DB 로 확인했는가** | **아니다.** 이 라운드는 백테스트 미실행(`--dry-run` 까지)이 전제였다. 검증은 가짜 연결로 *"그 실행옵션이 실제로 전달되는가"* 까지만 했다(검사 2건) |
| 5,000행이 **드라이버 쪽에서 몇 바이트**인가 | **[미측정].** DB 없이는 못 잰다. 파이썬 객체(383B/행)와 다른 표현이다 |
| 서버(postgres) 쪽 커서 비용 | **[미측정].** db 컨테이너는 `mem_limit 192MB` 다 |
| **첫 실행 때 할 일** | 로그의 `순간 보유 행 최대 N[청크 C + 뷰](상한 …)` 세 숫자와 함께 `docker stats` 로 API/db 컨테이너 RSS 를 같이 본다. 그 값을 이 표에 적어 `[미측정]` 을 지운다 |

## 8. 실행 (아직 돌리지 않았다)

`backend/` 에서 돌린다(다른 스크립트와 같다 — `_common` import 가 `sys.path` 를 세운다).

```bash
cd backend
# --dry-run 은 DB 에 닿지 않는다. 백필이 도는 동안에도 계획을 확인할 수 있다.
python scripts/run_backtest.py --folds 2022-01-31,2023-01-31 --dry-run

export DATABASE_URL=postgresql+psycopg://...
python scripts/run_backtest.py --as-of 2025-01-31 --top-n 30 --json out.json
python scripts/run_backtest.py --folds 2022-01-31,2022-07-31,2023-01-31 \
    --scorer current_weights --top-n 30

# 축 단독 실행(§6-2) — 축 하나가 무작위를 못 이기면 제거가 먼저다
for s in price_attractiveness liquidity price_trend random constant; do
  python scripts/run_backtest.py --folds 2022-01-31,2023-01-31 --scorer "$s"
done

# 해제 정책 상·하한(§2-D) — 결론이 갈리면 결론을 내지 않는다
python scripts/run_backtest.py --as-of 2025-01-31 --cancellation exclude_final --json lo.json
python scripts/run_backtest.py --as-of 2025-01-31 --cancellation include_all   --json hi.json
# 생존 편향 민감도(§3-D)
python scripts/run_backtest.py --as-of 2025-01-31 --unmeasured benchmark
```

* 스크립트는 **읽기 전용 SELECT** 만 한다. 어떤 테이블에도 쓰지 않는다.
  세션이 `SET TRANSACTION READ ONLY` + `SET default_transaction_read_only = on` 으로
  시작하고, **가드가 실제로 걸렸는지 `SHOW transaction_read_only` 로 DB 에 되묻는다**
  (AUTOCOMMIT 연결이면 아예 거부한다 — §7-14-B). 그래도 그것이 '차단'은 아니다 — **§7-14**.
* 운영 DB 는 `mem_limit 192MB` 다 — `build_market_index.py` 와 같은 규칙을 따른다:
  시군구 단위로 나눠 읽고, 세션 `statement_timeout`·`work_mem` 을 명시하고, 사이에 쉰다.
* **클라이언트 쪽 메모리에도 상한이 있다**(§5-1 · §7-13). 거래는 청크(기본 5,000행)로만
  손에 쥐고, 드라이버도 같은 수만 버퍼한다(`stream_results` — §7-13-B).
  로그에 `순간 보유 행 최대 N[청크 C + 뷰](상한 2×chunk_rows) · 누적 표본 K` 가 찍히므로
  실행 직후 그 숫자들을 확인할 것 — **N 은 청크의 2배까지 정상**이다(as-of 뷰의 마스킹 사본).
  상한을 넘으면 결과를 만들지 않고 멈춘다.
  조절: `--chunk-rows`(행 상한) · `--max-samples`(표본 상한).
* 결과 JSON 에는 **개인 정보가 들어가지 않는다** — 셀 식별자(`complex_id`)와 통계뿐이다.
  대신 `params` 블록에 **재현에 필요한 값 전부**(`cancellation`·`min_trades`·
  `min_peer_cells`·`report_lag_days`·`seed`·`null_draws`·`chunk_rows`…)가 실린다.
  ⚠️ 해제 정책 상·하한을 두 번 돌릴 때 **두 파일이 서로 어느 끝인지 파일 내용이 말한다**
  — 이게 없으면 나중에 아무도 증명할 수 없다(CR49-4).
