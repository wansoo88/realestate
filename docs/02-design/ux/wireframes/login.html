근거: ux/README.md §1(설계 기준) §5(신뢰 표시) · api-spec.md §1 · security.md

왜 로그인이 첫 화면인가: 이 서비스는 공개 엔드포인트가 없다(api-spec §0). 개인 자산 기반 판단이라 비로그인 상태로는 보여줄 게 없다. 그래서 로그인 화면이 곧 첫인상이고, 여기서 "내 소득을 넣어도 되는 서비스인가"가 결정된다.

전체 로그인 조건 입력 3단계 리포트 상세

1. 로그인

왜 이 배치인가: 입력 필드는 위, 실행 버튼은 하단에 둔다. 폰을 한 손으로 쥔 상태에서 엄지가 닿는 곳은 화면 하단 1/3뿐이다(README §1). 제출 버튼이 폼 바로 밑에 붙어 있으면 화면 중앙이라 엄지가 닿지 않는다.

구현 요건 (re-fe)
  • 제출 버튼은 scr__foot에 고정. 키보드가 올라와도 가려지지 않게 — iOS Safari는 position:fixed가 키보드와 겹친다. 플렉스 레이아웃 + 100dvh를 쓴다.
  • autocomplete="username" / "current-password" 필수 — 비밀번호 관리자가 못 채우면 사용자는 짧은 비밀번호를 쓴다(보안 UX).
  • 오류는 필드 아래 + role="alert". 상단 토스트는 폼을 보는 눈높이에서 벗어나 놓친다.
  • 오류 문구는 "이메일 또는 비밀번호"로 합친다 — 어느 쪽이 틀렸는지 알려주면 계정 존재 여부가 새어나간다(security.md).
  • 비밀번호 표시 토글은 44×44px, aria-pressed로 상태 노출.
  • 확대 금지(maximum-scale) 하지 않는다 — 이미 지켜지고 있음(frontend/index.html).
  • 🔒 신뢰 문구는 로그인 화면에도 둔다. 자산 입력 화면에서 처음 보면 그때 이탈한다.

2. 계정 만들기

왜 최소 필드인가: 사용자는 1명(본인)이다. 이름·전화·약관 동의를 받을 이유가 없다. 받지 않은 개인정보는 유출될 수 없다(security.md 데이터 최소화).

구현 요건 (re-fe)
  • 비밀번호 규칙은 입력 전부터 보이게 한다. 제출 후 빨간 글씨로 알려주는 건 최악의 순서다.
  • 규칙 충족 여부를 색뿐 아니라 텍스트 배지("충족/미충족")로 — 색만으로 정보 전달 금지(README §11).
  • 규칙 목록은 aria-describedby로 비밀번호 입력과 연결해 스크린리더가 함께 읽게 한다.
  • 가입 성공 → 자동 로그인 → 온보딩 1단계로 직행. 로그인 화면으로 되돌리지 않는다.
