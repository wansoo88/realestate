## 0. 설계 전제 — 왜 AWS 3-tier가 아닌가

스캐폴드 템플릿은 AWS 3-tier를 전제하지만, 이 프로젝트는 **이미 보유한 iwinv VPS 한 대**에 배포한다.
사용자가 **1명**(추후 가족·지인)이고 일정이 2~3개월이므로, 멀티 AZ·오토스케일링·관리형 서비스는 **명백한 과설계**다.

대신 **Docker Compose로 서비스 경계를 미리 나눠둔다.** 지금은 한 호스트에서 돌지만,
나중에 사용자가 늘면 컨테이너 단위로 분리·이전할 수 있다. 즉 **"단순하게 시작하되 쪼갤 수 있게"** 가 원칙이다.

---

## 1. 구성 요소

| 컨테이너 | 역할 | 외부 노출 |
|---|---|---|
| `nginx` | TLS 종단(Let's Encrypt), React 정적 빌드 서빙, `/api` 리버스 프록시, rate limit | **443/80만** |
| `api` | FastAPI. 인증(JWT), 매물·단지 조회, 자산 프로필 CRUD, 추천 요청 접수 | 내부 |
| `worker-agent` | 전문가 에이전트 8종 오케스트레이션. Claude API 호출, 근거 리포트 생성 | 내부 |
| `worker-ingest` | 공공API·포털 수집 배치. 정규화·중복제거·적재 | 내부 |
| `redis` | 작업 큐 + 분석 결과 캐시 | 내부 |
| `db` | PostgreSQL 16 + PostGIS. 공간쿼리·실거래 이력·자산 프로필 | **미개방** |

> 외부 의존: 카카오맵 API(브라우저 직접 호출), 공공 오픈API·포털(worker-ingest), Anthropic Claude API(worker-agent).

## 2. 트래픽 흐름

### 2.1 지도 탐색 (동기 · 빠름)
```
브라우저 → nginx(443) → api → db(PostGIS ST_Intersects)
                                 └→ 화면 범위 내 단지/매물 반환
브라우저 → 카카오맵 API (지도 타일·좌표 변환은 클라이언트에서 직접)
```
**목표: 1초 이내.** 지도를 움직일 때마다 호출되므로 여기가 느리면 서비스가 죽는다.
→ GiST 공간 인덱스 + 줌 레벨별 집계(개별 매물이 아니라 단지 단위 군집 반환).

### 2.2 AI 추천 (비동기 · 느림)
```
브라우저 → api : POST /recommendations  (조건 제출)
api      → redis : 작업 적재 → 즉시 202 + job_id 반환
worker-agent ← redis : 작업 소비
             ├→ db : 후보 매물·시세·입지·정책 데이터 조회
             ├→ (규칙 계산) 세금·대출한도 → 실구매 가능 금액
             ├→ Claude API : 에이전트별 분석·근거 문장 생성
             └→ db/redis : 결과 저장 + 캐시
브라우저 → api : GET /recommendations/{job_id}  (폴링 또는 SSE)
```
**왜 비동기인가**: 에이전트 8종이 순차·병렬로 Claude API를 호출하면 **수십 초**가 걸린다.
HTTP 요청 스레드에서 처리하면 게이트웨이 타임아웃이 나고, 모바일에서는 화면이 멈춘 것처럼 보인다.

### 2.3 데이터 수집 (배치)
| 주기 | 대상 |
|---|---|
| 일 1회 (새벽) | 국토부 실거래가 |
| 수 시간 | 포털 매물 호가 |
| 주 1회 | 공시가격·건축물대장·학교·교통·인구, 정책 고시 |

## 3. 핵심 설계 결정과 근거

| # | 결정 | 근거 |
|---|---|---|
| D1 | **단일 호스트 + Docker Compose** | 사용자 1명. 관리형 서비스 비용·운영부담이 이득보다 크다. 컨테이너 경계는 유지해 이전 가능성 확보 |
| D2 | **worker를 api에서 분리** | AI 분석 수십 초 → 요청 스레드 점유 시 타임아웃. 수집 배치가 API 응답성을 잡아먹지 않게 격리 |
| D3 | **worker-agent와 worker-ingest 분리** | 실패 격리. 수집이 밀려도 추천은 동작해야 하고, 반대도 마찬가지 |
| D4 | **redis에 분석 결과 캐시** | Claude API 호출이 **주 변동비**. 같은 조건 재요청 시 재계산은 순수 낭비 |
| D5 | **카카오맵은 브라우저에서 직접** | 지도 타일을 서버가 중계하면 대역폭·지연 손해. 무료 쿼터도 클라이언트 기준이 유리 |
| D6 | **PostGIS 필수** | "지도 화면 범위 내", "역에서 500m", "학군 경계 내부" 가 전부 공간쿼리. MySQL로는 인덱스가 안 먹는다 |
| D7 | **DB 포트 외부 미개방** | 공인 IP 노출 서버. 5432가 열려 있으면 자동화 공격 대상 1순위 |
| D8 | **세금·대출은 규칙 계산, LLM 아님** | 금액 계산을 LLM에 맡기면 틀린다. LLM은 **설명**만, 숫자는 코드가 |

## 4. 단일 장애점 (SPOF) — 정직하게

**서버가 하나다. 이건 아키텍처의 약점이고, 감수하기로 한 트레이드오프다.**

| 위험 | 영향 | 대응 |
|---|---|---|
| 서버 다운 | 서비스 전면 중단 | 개인용이므로 수 시간 중단은 감내. 재구축은 Compose로 수 분 |
| 디스크 손상 | **수집 데이터 전부 소실** | `pg_dump` 일 1회 + **오프사이트 보관**(서버 밖). 이게 유일한 방어선 |
| 실거래가 재수집 | 공공API로 복구 가능(느리지만) | 백업 실패해도 원천은 살아있음 |
| 자산 프로필 소실 | 복구 불가 (사용자 입력 데이터) | 백업 대상 최우선 |

> ⚠️ **백업을 서버 안에만 두면 백업이 아니다.** 오프사이트 복사를 반드시 구성할 것.

## 5. 성능 목표와 병목

| 경로 | 목표 | 병목 후보 | 대응 |
|---|---|---|---|
| 지도 범위 조회 | < 1초 | 매물 수천 건 직렬화 | 줌 레벨별 군집 집계, 단지 단위 반환 |
| 단지 상세 | < 1초 | 실거래 이력 수백만 행 스캔 | 단지ID+거래일 복합 인덱스, 파티셔닝 |
| AI 추천 | 수십 초 (비동기) | Claude API 왕복 | 에이전트 병렬 호출, 결과 캐시, 진행률 표시 |
| 수집 배치 | 야간 창 내 | 공공API rate limit | 지역별 분할, 증분 수집 |

**데이터 규모 추정(가정)**: 수도권 아파트 실거래 10년치 약 **200~300만 행**, 단지 마스터 약 2만 건,
동/타입 조합 수십만 건. → 중규모. 단일 PostgreSQL로 충분하되 **인덱스 설계가 성능을 좌우**한다.
> 이 수치는 추정이며, `re-data`/수집 1차 실행 후 실측으로 교체할 것.

## 6. 비용 구조

| 항목 | 성격 | 비고 |
|---|---|---|
| VPS | **고정비** | 이미 보유 — 추가 비용 없음 |
| 카카오맵 API | 무료 쿼터 내 | 개인 사용량은 여유 |
| 공공 오픈API | 무료 | 일일 호출 한도만 관리 |
| **Claude API** | **변동비 · 주 비용** | 추천 1회당 에이전트 8종 호출 → **캐싱과 모델 선택이 비용을 결정** |

> Claude API 단가와 추천 1건당 실제 토큰 사용량은 **구현 후 실측**해서 이 표를 갱신한다.
> 추정치를 지금 적으면 틀린 숫자가 근거처럼 굳는다.

**비용 통제 장치(설계에 반영)**
1. 분석 결과 캐시(같은 단지·같은 조건 재요청 시 재호출 없음)
2. 규칙으로 풀 수 있는 계산(세금·대출한도·점수 집계)은 LLM에 보내지 않음
3. MVP는 에이전트 5종만 — 8종 전체 호출은 2차

## 7. 확장 경로 (필요해질 때만)

```
지금:      [VPS 1대] 전 컨테이너
    ↓ 사용자 증가
1단계:     db 를 별도 호스트/관리형으로 분리 (가장 먼저 아픈 곳)
    ↓
2단계:     worker-agent 수평 확장 (큐 소비자 N개)
    ↓
3단계:     nginx 앞에 CDN, 정적 자산 분리
```
> **지금 하지 않는다.** 사용자 1명에게 오토스케일링은 낭비다. 아픈 순서대로 쪼갠다.

## 8. docker-compose 골격 (3단계 구현 시 확정)

```yaml
services:
  nginx:      { ports: ["80:80","443:443"], depends_on: [api] }
  api:        { build: ./backend, env_file: .env, depends_on: [db, redis] }
  worker-agent:  { build: ./backend, command: "celery -A app worker -Q analyze" }
  worker-ingest: { build: ./backend, command: "celery -A app worker -Q ingest" }
  redis:      { image: redis:7 }
  db:         { image: postgis/postgis:16-3.4, volumes: [pgdata:/var/lib/postgresql/data] }
              # ⛔ ports 를 열지 않는다 — 내부 네트워크 전용
```
> 큐 구현(Celery vs RQ vs FastAPI BackgroundTasks)은 3단계 구현계획에서 확정. 지금 단정하지 않는다.
