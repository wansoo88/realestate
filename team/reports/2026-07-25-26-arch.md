## (3) 004 마이그레이션 — INGEST-2 조율 반영 (rev 1 중 지시)

**결론: 컬럼 변경이 필요 없었다. 자연키는 이미 `is_cancelled` 를 제외하고 있었다.**
```sql
UNIQUE NULLS NOT DISTINCT (complex_id, contract_date, price_krw, area_m2, floor)
```
요청된 정의(complex_id·면적·contract_date·floor·price_krw, is_cancelled 제외)와 **동일**하다.

다만 기존 주석은 "중복 적재 방지" 관점만 적혀 있어, **왜 `is_cancelled` 가 들어가면 안 되는지**가
드러나지 않았다. 그 상태로 두면 나중에 "해제도 이력으로 남기자"며 컬럼을 키에 추가하는
변경이 리뷰를 통과할 수 있고, **그 순간 방어가 조용히 깨진다.** 그래서 두 가지를 보강했다.

1. **마이그레이션 주석에 공격 시나리오를 명시** — 높은 가격에 계약 → 신고 → 해제.
   해제 신고가 별도 행으로 들어오면 허위 고가 행이 살아남아 시세가 위로 조작된다.
   제약 COMMENT 에도 "is_cancelled 는 **의도적으로 제외**(INGEST-2)" 를 남겼다.
2. **회귀 테스트 `test_INGEST2_해제거래_시세조작이_막힌다` 추가** — 공격을 그대로 재현하고
   (정상 15억 + 허위 30억 → 해제 신고), 허위 고가가 `is_cancelled=true` **한 행으로
   갱신**되는지 확인한다. 더해 `pg_constraint` 를 직접 조회해 자연키 컬럼 집합을 단언한다:
   ```
   assert "is_cancelled" not in cols
   assert set(cols) == {complex_id, contract_date, price_krw, area_m2, floor}
   ```
   누가 키에 컬럼을 더하면 이 테스트가 바로 깨진다.

**면적은 `area_m2`(원본)를 쓰고 `unit_type_id` 는 쓰지 않았다.** 지시서 표현이
"unit_type/면적"이라 짚어 둔다 — `unit_type_id` 는 면적으로 되찾는 **파생값**이라
매칭 실패 시 NULL 이 되고, unit_type 이 나중에 적재되면 **같은 거래의 키가 바뀐다.**
키가 흔들리면 dedup 자체가 무너진다. re-data 의 확정 정의가 `unit_type_id` 를 요구하면
바꿀 수 있으나, 위 이유로 `area_m2` 를 권한다.

## (3-1) 004 마이그레이션 상세
**trade 자연키** — `UNIQUE NULLS NOT DISTINCT (complex_id, contract_date, price_krw, area_m2, floor)`
- 파티션 테이블이라 파티션 키(`contract_date`)가 자연키에 포함돼야 성립한다 — 들어 있다.
- **`NULLS NOT DISTINCT` 가 핵심**이다. 기본 동작에서는 NULL 끼리 다른 값으로 취급돼
  유니크가 안 걸리는데, 원본에서 `floor`·`area_m2` 가 비는 행이 **중복이 가장 많이
  생기는 자리**다. 기본값으로 뒀으면 막으려던 걸 정확히 못 막았을 것이다. (PG15+ 문법, 서버는 PG16)
- 적재는 `ON CONFLICT ... DO UPDATE SET is_cancelled = EXCLUDED.is_cancelled` —
  해제 여부는 나중에 바뀌어 다시 내려오므로 갱신 대상이다.

## `recommendation_item.payload` — **승인됨 → 005 로 분리** (rev 2)

re-pm 승인: *"headline·why·why_not·next_actions·판단보류사유가 응답에서 사라지면
추천이 반쪽이다."* 지시대로 **005 마이그레이션으로 분리**했다.

- `004_trade_natural_key.sql` — trade 자연키만 (re-data·INGEST-2 관심사)
- `005_recommendation_item_payload.sql` — payload 만 (리포트 렌더링 관심사)

**분리가 오히려 낫다**: 마이그레이션 하나가 바뀔 이유가 하나씩이고, payload 를
되돌려야 할 때 자연키를 건드리지 않는다. 둘 다 아직 어떤 DB 에도 적용된 적이 없어
(커밋 전·미적용) 분리에 위험이 없음을 먼저 확인했다 — 적용된 마이그레이션이었다면
편집하지 않고 006 으로 갔을 것이다.

`agent_finding` 의 CHECK 는 **그대로 뒀다**(근거 있는 finding 만). 지시대로다.

아래는 승인 요청 당시의 근거 — 기록으로 남긴다.

파이프라인 항목에는 `headline`·`why`·`why_not`·`next_actions` 와 각 finding 의
`risks`·`missing` 이 들어 있다. **이 리포트 본문이 곧 제품인데** `recommendation_item`
컬럼(rank·total_score·est_price_krw·timing_signal)에는 담을 자리가 없다.
정규화 컬럼만으로 복원하면 사용자는 **순위와 점수만 보고 "왜 이 단지인지"를 못 본다.**

여기에 더해 `agent_finding` 은 `CHECK (jsonb_array_length(evidence) > 0)` 이라
**근거 없는 '판단 보류' finding 을 저장할 수 없다**(의도된 G2 설계). 그대로 두면
"왜 판단을 보류했는지"까지 사라진다.

payload 를 넣으면 PostGIS 응답이 인메모리와 **완전히 같아진다**(계약 파리티).
정규화 컬럼과 `agent_finding` 은 그대로 둔다 — payload 는 '보여줄 것',
컬럼은 '따질 것'(집계·근거 감사)이다.

**저장·복원 경로**(승인 후 확인):
- `save_job_result` → `_insert_item` 이 항목 원본을 `payload` 로 저장.
- `get_job` → `_item_to_dict` 가 payload 를 그대로 복원(단, `id`·`rank` 는 DB 값이 정본).
- payload 가 NULL 인 옛 행은 정규화 컬럼으로 최소 복원 — 기존 데이터가 있어도 깨지지 않는다.
- 회귀 테스트가 승인 문구의 **다섯 가지를 하나씩** 단언한다:
  `headline` · `why` · `why_not` · `next_actions` · 판단보류 finding의 `rationale`/`missing`.

## 이슈 / 잔여 위험
1. **실행 검증은 여전히 못 했다** — 로컬에 DB 없음. needs_db 34→**49건**으로 늘려
   두 놨고, 배포 서버 검증 때 한 번에 돈다. 정적으로는 바인드 파라미터·시그니처·
   Protocol·참조 컬럼을 대조했다.
2. **법정동코드 파일 형식을 공식 문서로 확인하지 못했다.** code.go.kr 페이지에 컬럼·
   구분자·인코딩 명세가 없다(문의처만 안내). 그래서 파서를 **관용적으로** 짰다 —
   인코딩 추정, 탭·쉼표 모두 수용, 10자리 숫자가 아닌 행은 건너뜀. 실제 파일로
   `--dry-run` 을 먼저 돌려 파싱 결과를 눈으로 확인하는 절차를 스크립트에 넣었다.
3. **`resolve_region_code` 는 지번주소 전용이다.** 도로명주소는 동 정보가 없어 None 이
   된다(추정하지 않는다). 포털 수집이 도로명만 준다면 별도 변환(카카오 지오코딩 등)이
   필요하다 — re-data 확인 요망.
4. **판단 보류 finding 은 `agent_finding` 에 남지 않는다.** 스키마 설계(G2)가 그렇고,
   사유는 payload 로 보존했다. 다만 "어떤 에이전트가 왜 기권했는지"를 **SQL 로 집계할 수
   없다.** 필요해지면 `agent_finding` 에 abstain 계열 컬럼을 두는 설계 변경이 필요하다
   → re-review·re-domain 판단 사항.
5. `_TRADE_HISTORY_LIMIT = 2000` 은 내가 정한 상한이다(시세는 최근 36개월만 보므로
   충분하다고 판단). 대단지에서 부족하면 조정 필요.
