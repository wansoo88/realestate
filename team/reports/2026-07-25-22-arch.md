## DEP-2 (blocker) — 인증서 발급 순서
**문제**: 443 블록의 `ssl_certificate` 가 certbot 이전에 요구돼 `nginx -t` 가
`cannot load certificate` 로 실패 → 절차가 §5-4 에서 막힌다.

**수정**: 리뷰의 ⓐ안(부트스트랩 + `certonly --webroot`)을 택했다.
- 신규 `deploy/nginx-realestate-bootstrap.conf` — **HTTP 전용, `ssl_certificate` 참조 0건,
  `listen 443` 0건**(정적 검증으로 확인). ACME 챌린지 경로만 열고 나머지는 404 로 막는다
  (발급 단계에서 평문 HTTP 로 인증 API 를 노출할 이유가 없다).
- DEPLOY.md §5-5 를 4단계로 재작성: 부트스트랩 배치→`nginx -t`→발급→본 설정 교체→`nginx -t`→reload.

**ⓑ(주석 처리) 대신 ⓐ를 고른 이유**: ⓑ는 운영자가 라이브 설정 파일을 **손으로 편집**하게
만든다. 리뷰가 짚은 진짜 위험("막힌 상태에서 운영자가 손으로 고치려 드는 것")과 같은
행동을 절차가 요구하는 셈이다. 파일 교체는 손 편집이 없다.

**`certbot --nginx` → `certonly --webroot` 로 바꾼 것도 같은 이유**다. `--nginx` 는 nginx
설정을 **자동으로 고쳐 쓴다.** 동거 서비스 설정이 있는 서버에서 자동 수정은 위험하다.
`certonly` 는 인증서만 받고 설정은 건드리지 않는다.

막혔을 때 손대지 말고 되돌리는 절차(심링크 제거→`nginx -t`→reload)도 §5-5 에 넣었다.

## DEP-1 (medium) — `add_header` 상속 소실
**문제**: 하위 location 에 `add_header` 가 하나라도 있으면 상위 `add_header` 를 전혀
상속하지 않는다. `= /index.html` 과 정적 자산 location 이 Cache-Control 을 붙이면서
보안헤더 4종이 통째로 탈락 → **사용자가 실제로 여는 화면에서 클릭재킹 방어가 사라진다.**

**수정**: 두 location 에 4종을 다시 명시. 정적/설정 검증으로 확인했다:
```
[inherit] /                                : add_header 없음 → 서버 4종 상속
[inherit] /api/ · auth · acme-challenge    : 동일
[OK]      ~* \.(js|css|woff2?|png|jpg|svg)$: 5 headers (4종 재명시)
[OK]      = /index.html                    : 5 headers (4종 재명시)
```
(주석 속 `add_header` 를 세지 않도록 주석을 걷어내고, 중첩 location 을 제외한
**직속 지시자만** 세는 방식으로 검사했다.)

**§5-6 검증도 고쳤다** — 이게 더 중요하다. 기존은 `grep -i strict-transport` 한 줄이라
빈 결과가 나와도 눈으로 넘어갔다. 이제 `check_headers()` 가 경로별로 4종을 돌며
하나라도 없으면 `[실패]` 를 찍는다. 검사 대상도 `/` · `/index.html` · `/api/v1/health` ·
실제 정적 자산으로 넓혔다(`/` 가 try_files 내부 리다이렉트로 index.html 을 타는 게 핵심 경로).

## DEP-3 (권고) — 빌드를 db 기동 앞으로
**문제**: `docker build` 는 `mem_limit` 의 보호를 받지 않는다. db 가 뜬 뒤 빌드하면
남은 ~254MB 에서 돌고, 여기서 OOM 이 나면 cgroup 이 아니라 **호스트 전역 OOM killer** 가
돈다 — 희생자는 RSS 최대인 autobtc(195MB)가 되기 쉽다.

**수정**: `build api` 를 §5-2 로 올려 `up -d db`(§5-3) 앞에 뒀다. 빌드가 400MB 를 온전히 쓴다.
확인: `build api`(L148) < `up -d db`(L170) < `up -d api`(L187).

리뷰가 제안한 "더 나은 방법"(로컬 빌드 → `docker save | ssh docker load`)도 대안으로
문서에 적었다. **프론트를 로컬 빌드하기로 한 것과 같은 원칙**이라 일관성 지적이 옳았다.
다만 기본 절차는 서버 빌드로 뒀다 — 이미지 전송(수백 MB)이 회선에 따라 더 번거롭고,
순서 변경만으로 위험 구간이 사라지기 때문이다. 필요하면 대안으로 바꿀 수 있게 둘 다 적었다.

## 이슈 / 잔여 위험
1. **`nginx -t` 를 실제로 돌려보지 못했다.** 로컬에 nginx 가 없다. 문법·구조는 정적으로
   검증했지만 최종 판정은 서버에서 난다. 다만 절차가 `nginx -t` 게이트를 두 번(부트스트랩·본
   설정) 거치므로, 실패해도 reload 전에 멈추고 되돌리는 경로가 §5-5 에 있다.
2. **`add_header` 상속 함정은 앞으로도 재발하기 쉽다.** location 을 하나 추가하면서
   Cache-Control 만 붙이면 그 경로만 조용히 무방비가 된다. conf 상단에 규칙을 적어 뒀고
   §5-6 이 경로별로 검사하지만, **구조적으로 막지는 못했다.** 근본 대응은 헤더를 별도
   snippet 파일로 빼고 `include` 하는 것인데, DEP-2 에서 배운 대로 include 는 파일이
   없으면 `nginx -t` 를 깨뜨린다 — 지금은 반복 명시가 더 안전하다고 판단했다.
3. 19-arch 의 잔여 위험(수집 데이터 없음·추천 미동작·DB 백업 미설정·서버 하드닝 미적용)은
   **그대로 남아 있다.** 이번 수정 범위가 아니다.
